# Активация агентов MYDON — runbook владельца

Все «умные» части агентов построены и покрыты тестами, но **спят по умолчанию**:
без ключей/шлюзов агенты работают детерминированно (смотрят Core, предлагают
дело, молчат когда повода нет). Этот файл — единственная точка правды: какие
тумблеры щёлкнуть, чтобы включить мозг, память и самоулучшение, и что каждый
включает.

Принцип безопасности сквозной: **агент ничего не делает сам** — он пишет событие
и создаёт запрос на согласование (HITL). Автономия по умолчанию `T0` (только
предлагает). Собственные LLM-шлюзы и embed-модель держать **только внутри
Tailscale**; официальный OpenAI API вызывается напрямую по HTTPS, без прокси.

## Два способа щёлкать тумблеры

- **Из панели** (`Система · Активация`) — не-секретные глобальные тумблеры
  (LLM-маршрут/модель/бюджет, RAG, пауза, автономия) хранятся в базе Core и
  **перекрывают `.env`**.
  Правки действуют без пересборки: агенты накладывают их при перечитке. Это
  рекомендуемый путь для владельца — с телефона, без доступа к серверу.
- **Через `.env`** — то же самое на уровне окружения (когда базы ещё нет или для
  первичной настройки). Внутри одного ключа приоритет: **база > env > дефолт**.
  Новый `LLM_GLOBAL_DAILY_BUDGET_USD` важнее legacy
  `AGENT_GLOBAL_BUDGET_USD`. Новая установка получает `$10`; явно сохранённый
  старый cap существующей установки не повышается при rollout и переносится в
  новый профиль при первом сохранении.
- **Секреты (API-ключи) — только в серверном `.env`.** В панели их принципиально нет
  (правило ТЗ). `LLM_PRICE_PROVIDER_ID` и `EMBED_PRICE_PROVIDER_ID` доступны в
  панели, потому что это не ключи и не URL, а literal ID ценового профиля из
  `llm_model_price.provider`. Для рабочего metered HTTP-пути секрет шлюза
  остаётся только в `.env`.
- `LLM_HTTP_BILLING_MODE` и `EMBED_BILLING_MODE` тоже намеренно **только в
  `.env`**. Значение `local` обходит денежный ledger, поэтому этот опасный
  monetary bypass нельзя включить случайным кликом из панели.

## Сценарий 1а — почему Codex/ChatGPT subscription заблокирован

В интерфейсе первоначально выбран рабочий `openai-api`; `codex-subscription`
оставлен как явно недоступный вариант. Вход через ChatGPT подтверждает аккаунт,
но не источник оплаты следующего turn. После исчерпания включённого лимита
доступные ChatGPT credits позволяют продолжить работу, а CLI не предоставляет
MYDON машиночитаемый pre-turn режим «included-only». Поэтому запись такого
вызова в едином ledger как `$0` была бы ложной. Попытка включить профиль
отклоняется до запуска процесса или HTTP-вызова; скрытого перехода на API нет.

Для агентов используй метрируемый OpenAI API-путь из сценария 1б. Подписочный
маршрут можно будет включить только после появления официального серверного
механизма, который до каждого turn доказывает отсутствие отдельной оплаты.

[Официальные правила лимитов и ChatGPT credits для Codex](https://learn.chatgpt.com/docs/pricing).

Что оживает после настройки HTTP: навык `assess-ideas` (оценка фишек
канала моделью), петля coach (EVAL/PROPOSE) и `find-solution`
агента `solution-scout` для порученных Core-задач. Без шлюза `assess-ideas`
и coach честно спят. Порученная `find-solution` задача не превращается
в ложный `no_signal`: она остаётся открытой, worker сообщает
`ledger_unavailable` и не делает provider call. Одна лишь настройка HTTP также
не снимает паузу порученных задач.

## Сценарий 1б — включить GPT-5.6 Sol через OpenAI API

1. Миграция `0078_openai_gpt_56_sol` добавляет первоначальный ценовой профиль
   `provider=openai`, `model=gpt-5.6-sol`. До каждого rollout сверить его с
   [официальной карточкой GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol);
   promotional-тариф истекает в ledger `2026-11-22T00:00:00Z`, после
   чего вызовы fail-closed до новой dated-миграции с актуальной ценой.
2. Создать API-ключ в OpenAI Platform и записать его **только** в серверный
   `.env`; значение никогда не вводится и не возвращается через панель:
   ```dotenv
   LLM_API_KEY=<секрет>
   LLM_BASE_URL=https://api.openai.com/v1
   LLM_PRICE_PROVIDER_ID=openai
   LLM_MODEL=gpt-5.6-sol
   LLM_ROUTE=openai-api
   LLM_HTTP_BILLING_MODE=metered
   ```
3. Пересоздать контейнер Agents, чтобы он получил новый server env (уже
   запущенный контейнер изменение `.env` не увидит):
   ```bash
   docker compose -f deploy/docker-compose.yml up -d --force-recreate mydon-agents
   ```
4. В панели `Система · Активация` проверить модель и маршрут, установить
   `$10` в сутки и `$3` на один reserve, затем явно включить LLM. Сохранение
   профиля атомарное: несовместимый набор не применяется частично.
5. Для Agents дополнительно проверить `AGENT_DAILY_BUDGET_USD` либо
   `budget.per_day_usd` в карточке агента. Запрос с input больше 272 000 токенов
   пока отклоняется: повышающий тариф длинного контекста намеренно не оценивается
   плоской ставкой.

Для нового рабочего профиля `openai-api` режим всегда `metered`: exact endpoint,
provider, модель, серверный ключ и действующая цена проверяются до reserve и
HTTP-вызова; никакого неявного `openai-compatible` или fallback нет. Успешный
ответ обязан сообщить фактическую модель;
отсутствие `usage.cost` не считается доказательством нулевой цены. Core сам
классифицирует неполный или несовместимый settlement и при routing anomaly
открывает provider circuit до ручной сверки либо новых ташкентских суток.

## Сценарий 1в — безопасный canary `solution-scout`

`find-solution` оживает только для задачи, которая в Core поручена
агенту `solution-scout`. Вход задачи атомарный: `title`, опциональные
`description` и `domain` входят в один `taskInput` и его hash. Если задачу
изменили после старта execution, старый результат не коммитится.

Поиск первого среза идёт по публичному GitHub через GET-only connector с
фиксированным хостом `api.github.com`. Он не переходит по `homepage`,
README-ссылкам или редиректам. Для public-вызова новый секрет не нужен:
не копируй GitHub CLI токен ни в панель, ни в production `.env`. Rate limit
или частичный отказ источника должен попасть в coverage gaps, а не маскироваться
под «ничего не найдено».

Порядок одного canary:

1. Убедиться, что миграция `0079_task_agent_input_snapshot` применена, Core и
   Agents healthy, `LLM_ENABLED=1`, маршрут — `openai-api / gpt-5.6-sol`,
   effective `LLM_FALLBACK_MODELS` пуст, а глобальный потолок автономии
   остаётся `T0`. Непустая fallback-chain может законно создать второй
   provider job после definitive rejection и потому не допускается в этом
   одноразовом canary.
2. Зафиксировать текущее effective-значение `AGENTS_SCHEDULES_PAUSED` и не менять
   его ради canary: пауза cron и task-worker — разные контуры. В текущем
   production schedules не на паузе (`0`), и в этом rollout они остаются
   в том же состоянии. Снять только `AGENTS_TASKS_PAUSED` и поручить
   `solution-scout` ровно одну тестовую задачу с короткими `title`,
   `description` и выбранным `domain`. В очереди не должно быть других
   порученных агентам задач.
3. До платного шага Core должен сохранить immutable snapshot с kind
   `solution-search-v1`. После него допускается ровно один physical
   ranking job `find-solution:rank` через durable LLM-ledger. Операционная
   цель первого canary — фактическая стоимость около `$0.01`: для этого
   шага используется `max_completion_tokens=192` и поддерживаемый GPT-5.6 Sol
   `reasoning_effort=none`, причём оба параметра входят в сохранённый exact
   provider request. Это не
   заменяет ledger-cap `$10/$3`, а ограничивается одним коротким job. Второй
   paid job в этом canary не запускать.
4. В карточке задачи принять только T1 proposal: ранжированный отчёт с
   canonical `https://github.com/<owner>/<repo>` links и честными coverage gaps.
   Canary считается успешным только при `facts.model.called=true` и
   `facts.model.valid=true`; `LLM output invalid/rejected; deterministic fallback`
   — диагностический результат, а не успешная проверка GPT-ranking.
   Для этого среза обязательно указать: GitHub-only; SaaS-каталоги,
   `n8n.io` и YouTube не искались; dependency/security advisory review
   incomplete; CVE не проверялись. Это отчёт, а не разрешение установить
   или запустить найденный код.
5. В `Система · LLM-мониторинг` сверить фактическую стоимость и модель,
   нулевые зависшие резервы и ошибки, закрытый circuit и пустую очередь
   закрытия ledger. В БД дополнительно сверить snapshot, один ranking job,
   один связанный `llm_spend` и Notion outbox по командам из
   [`DEPLOY.md`](DEPLOY.md).
6. Если хоть одна проверка не сошлась, не повторять paid call: сразу
   вернуть `AGENTS_TASKS_PAUSED=1`, не менять зафиксированное значение
   `AGENTS_SCHEDULES_PAUSED` и разобрать
   сохранённые evidence. Пауза task-worker не стирает snapshot/job/spend/outbox.

## Сценарий 1г — llm-навык (`executor: llm`): первый прогон `qualify-lead`

Навык без кода: исполнитель берёт тело `SKILL.md` паспорта, устав
`apps/agents/shared/COMPANY.md`, `ROLE.md` агента и страницы знаний из
`kb_pages` карточки, делает **ровно один** metered-вызов модели
(feature `llm-skill:<навык>`, тот же ledger и durable session, что у
`find-solution`) и превращает JSON-ответ в предложение во Входящих. Первый
такой навык — `globerent-sales/qualify-lead`. Спека и инварианты R-LS-1…12:
[`superpowers/specs/2026-09-04-llm-skill-executor-design.md`](superpowers/specs/2026-09-04-llm-skill-executor-design.md).

Что должно быть включено (сверх сценария 1в):

- Миграция `0083_agent_kb_pages` применена (`pnpm --filter @mydon/db db:migrate`).
- `AGENTS_TASKS_PAUSED=0`. Первый прогон — по порученной задаче. С 05.09 навык
  можно поставить и на расписание, и запустить кнопкой из панели `/skills`:
  см. раздел «Deck и cron для llm-навыков» ниже.
- Карточка агента в базе знает страницы знаний и границы роли. Seed при
  старте существующих агентов не трогает, поэтому один раз после деплоя:
  `docker compose … exec -T mydon-core node tools/apply-passport-fields.mjs --dry-run`,
  затем без `--dry-run`. Скрипт заполняет пустое и добавляет навыки, заданное
  владельцем не переписывает (`--overwrite=<поле>` — осознанно).
- Агент `globerent-sales` включён кнопкой в панели `/agents/globerent-sales`
  (в паспорте он `paused`; база — истина). Поле «Страницы знаний (KB)» в той же
  карточке должно содержать `heli-models.md`, `pricelist.md`, `lead-criteria.md`.

Порядок одного canary:

1. `pnpm --filter @mydon/agents check:passports` → «ИТОГ: все паспорта целые».
2. Поручить `globerent-sales` одну задачу, заголовок которой попадает в
   `triggers` навыка (`квалифиц…`, слово «лид», `lead`, «запрос на погрузчик»,
   «тендер», «выставк…»), например «Квалифицируй лид: OLMA, 3× CPD25, срочно».
   Подробности лида — в описании задачи: оно идёт модели **недоверенным
   блоком** (`untrustedContext`), инструкции внутри него не исполняются.
3. Ожидаемо: один immutable план с единственным шагом `llm-skill:qualify-lead`,
   один provider job, во Входящих — предложение T1 (пол тира считается как у
   любого навыка: `requires-approval` × `allowed-tools`). В `facts`: `details`
   (разбор по формату навыка), `model`, `costUsd`, `kbPages` (что реально
   прочитано, с пометкой «(обрезана)» при превышении `LLM_SKILL_KB_PAGE_CHARS`,
   по умолчанию 12 000 символов на страницу), `kbMissing`, `toolsIgnored`,
   `promptChars`, `contextMissing` (если нет COMPANY.md/ROLE.md в образе).
4. Модель ответила `summary: "нет повода"` → предложения нет, задача закрыта
   пометкой «повода нет» — как у кодовых навыков.
5. Ответ не по контракту или провайдер отклонил вызов → задача **блокируется**
   (`skill_failed`): в карточке задачи «Агент ждёт решения владельца» и текст
   причины с началом ответа модели. Повторной оплаты не будет — durable
   результат воспроизводится тем же, поэтому Core не даёт задаче крутиться
   claim→replay→release. Дальше: owner retry (одна новая платная попытка)
   или переназначение.
6. В `Система · LLM-мониторинг` сверить стоимость и модель, как в 1в п. 5.

Откат: выключить агента в панели (задачи ему не поручаются) или вернуть
`AGENTS_TASKS_PAUSED=1`. Убрать `executor: llm` из frontmatter навыка → он
снова `not_implemented`, как до этого среза. Колонка `kb_pages` имеет default
и откат кода не ломает; убирать её (`drop column`) — только после отката кода.

Следующий llm-навык: frontmatter (`executor: llm`, `requires-approval`,
`triggers`, `model-effort`, при необходимости `max-tokens`), `kb_pages` в
паспорте, `check:passports`, обновить список ожидаемых llm-навыков в
`skill-loader.test.ts` («qualify-lead — единственный executor: llm»), после
деплоя — `apply-passport-fields.mjs`. Расписание для такого навыка теперь
разрешено (`schedule:` в `config.yaml`) — раздел ниже.

## Deck и cron для llm-навыков

Срез 05.09 снял две границы спеки 04.09: навык теперь запускается **кнопкой из
панели**, а `executor: llm` **можно ставить на расписание**. Спека и инварианты
R-SD-1…10: [`superpowers/specs/2026-09-05-skills-deck-cron-llm-design.md`](superpowers/specs/2026-09-05-skills-deck-cron-llm-design.md),
решения с причинами — [`decisions/2026-09-05-skills-deck-cron-llm.md`](decisions/2026-09-05-skills-deck-cron-llm.md).

### Откуда берётся список навыков

Источник истины о навыке — его файл `apps/agents/agents/<агент>/skills/<навык>.md`
(frontmatter: `executor`, `requires-approval`, `triggers`, `model-effort`,
`allowed-tools`). Панель файлов не видит, поэтому **агенты при каждом успешном
старте переписывают каталог в Core целиком** (`PUT /agents/skills/catalog`, одна
транзакция «удалить всё → вставить всё»). Панель этот каталог только читает.

- `/skills` пуст и говорит «Каталог ещё не синхронизирован» → перезапусти
  контейнер агентов: `docker compose -f deploy/docker-compose.yml --env-file .env restart mydon-agents`.
- Навык удалён из файлов → он исчезает из панели следующим стартом агентов, а не
  остаётся кнопкой в никуда.
- Агент есть в файлах, но не заведён в базе → карточка `draft`, запуск
  заблокирован (заводится `tools/apply-passport-fields.mjs` или из панели).
- Проверить снаружи: `GET /agents/skills` → `{syncedAt, models, items[]}`;
  `syncedAt` ≈ время последнего старта агентов.

### Запустить навык из панели

1. Агент должен быть **включён** (`active`) в `/agents/<имя>`, а навык —
   закреплён за ним в карточке (поле «Навыки»). Иначе кнопка заблокирована, а
   API отвечает 409 с причиной: пауза уважается сразу, а не «worker всё равно не
   возьмёт». Не реализованные навыки (`executor: code` без кода в реестре
   агентов — таких в каталоге большинство) из deck не запускаются: кнопка
   заблокирована с подсказкой «навык ещё не реализован», Core отвечает 409.
2. `/skills` → карточка навыка → «Вход задачи» (необязательно; идёт модели
   **недоверенным блоком**, как описание задачи) → у llm-навыков select
   «Усилие» (`как в навыке | low | medium | high | xhigh`) → «Запустить».
3. Что происходит: создаётся **обычная задача агенту** (`ownerKind=agent`,
   `source=skills-deck`, `agent_skill=<навык>`, `run_options={modelEffort}`) —
   дальше тот же путь `task-worker → runner → policy → approval`. Ни тиры, ни
   бюджеты, ни `break_glass` не обходятся: кнопка поручает работу, а не поднимает
   автономию.
4. Результат — предложение во Входящих (или задача с причиной блокировки).
   Ссылка на задачу появляется прямо в панели после запуска, а последний запуск
   каждого навыка виден на его карточке (статус, когда, причина, `resultNote`).
5. Модель на карточке — глобальная цепочка (`LLM_MODEL` + `LLM_FALLBACK_MODELS`),
   **только показ**: per-run выбирается усилие, не модель (решение Р-4).

Деньги — как у любого llm-навыка: один metered-вызов через ledger
(`llm-skill:<навык>`), дневной бюджет агента и глобальный cap, сверка в
`Система · LLM-мониторинг`.

### Поставить llm-навык на расписание

1. В паспорте навыка — `executor: llm` (и `requires-approval`, `triggers`,
   `model-effort`, при необходимости `max-tokens`).
2. В `apps/agents/agents/<агент>/config.yaml` — строка расписания
   (часовой пояс — Asia/Tashkent):

   ```yaml
   schedule:
     - cron: "0 9 * * 1"   # понедельник, 09:00
       skill: <навык>
   ```

3. `pnpm --filter @mydon/agents check:passports` → «ИТОГ: все паспорта целые».
   llm в расписании больше **не** замечание: R-LS-11 снят.
4. LLM-маршрут должен быть **включён и metered** (`LLM_*` в `.env`): без него
   llm-навык в расписание не ставится вовсе и попадает в лог агентов строкой
   «Навыки без реализации (не планируются): <агент>/<навык> (LLM-маршрут
   выключен/не metered)». Включат ключ — расписание подхватится само на
   ближайшей перечитке (раз в 10 минут), перезапуск не нужен.
5. Деплой. На каждое срабатывание крона агенты создают **durable-задачу** в Core
   (`ensureAgentSchedule`, `clientKey = agent-schedule:v1:<sha256>` точного
   срабатывания) с `agent_skill = <навык>`; берёт её обычный worker.
   In-process платного вызова по крону нет и не будет: два способа запустить один
   навык — две разные истории списаний.
6. Пропущенное срабатывание не теряется (задача остаётся в очереди), двойное — не
   оплачивается дважды (тот же `clientKey` → replay).
7. **Повтор по расписанию не плодит согласования.** Предложение llm-навыка
   дедуплицируется по входу задачи И собранному промпту: одинаковые вход, KB и
   паспорт → `no_change`, во Входящих ничего нового. Новое согласование
   открывается только при смене входа, страниц знаний или паспорта (устав, роль,
   тело навыка). Поэтому описание задачи по расписанию НЕ содержит планового
   времени — точное время живёт в `due`.
8. Где смотреть: задача в списке задач агента (`source` = расписание), последний
   запуск — на карточке навыка в `/skills`, деньги — в LLM-мониторинге.

Откат: убрать `schedule:` из `config.yaml` (деплой) или выключить агента кнопкой
в панели — задачи ему перестают раздаваться. Убрать `executor: llm` из
frontmatter → навык снова `not_implemented`.

## Документы и Мозг

Панели `/docs` и `/brain` (волна M, `docs/decisions/2026-09-06-wave-m-docs-brain.md`) читают Core, а
не файловую систему CC и не GitHub: `GET /docs/tree|file|graph` отдаёт документы с диска ОБРАЗА
Core — того же, куда `COPY . .` кладёт паспорта агентов.

- **Что читают.** Белый список корней: `CLAUDE.md`; `docs/**/*.md` (кроме
  `docs/agentic-os-starter/_backup/**`); `memory/**/*.md`; `routers/*.md`; `engine/*.{yaml,md}`;
  `apps/agents/shared/**/*.md`; `apps/agents/agents/*/ROLE.md` и `.../skills/*.md`;
  `.claude/skills/*/SKILL.md` и `references/**/*.md`. Файл вне списка — 404 (`GET /docs/file`), путь с
  `..` за пределы репозитория — 400 (`normalizeDocPath`).
- **Токен — обязателен и на чтение.** Все три маршрута `docs/*` — за `DocsTokenGuard`: без
  `x-service-token` (или `Authorization: Bearer`) — 401, в отличие от остального read-only API Core,
  где GET открыт всем в закрытой сети.
- **Личные корни.** `memory/**`, `routers/personal.md` и профиль владельца из навыка фабрики
  направлений — личный контур: при включённом ужесточении owner-identity содержимое (не заголовок в
  дереве) отдаётся только по owner-токену (`x-owner-action-token`, 403 без него), теми же правилами,
  что остальной API (`personalVisible`).
- **Граф.** `/brain` рисует то, что построил `GET /docs/graph` в Core: документы + живые агенты
  (`archivedAt IS NULL`) + каталог навыков. Рёбра — markdown-ссылки (`links`) и пути в обратных
  кавычках на существующие файлы белого списка (`mentions` — на 208 файлов настоящих ссылок всего 25,
  без `mentions` граф распадался бы на острова). Оба ответа кэшируются в памяти Core 60 с.
- **Рендер.** `/docs` рендерит markdown через `marked` в панели: сырой HTML экранируется, ссылки на
  `.md` внутри белого списка ведут на `/docs?path=…`, внешние — `target=_blank`. Панель не тянет сеть
  и не исполняет чужой HTML — источник доверенный (свой репозиторий), но правило то же, что для любого
  чужого текста.

## Рутины: доска `/crons`, плейбэк `/flows`, хуки паспорта (волна R, 06.09)

Волна R (`docs/decisions/2026-09-06-wave-r-crons-flows.md`) даёт владельцу с телефона, без SSH,
ответ на два вопроса: что запустится в ближайшие 24 часа и почему навык вчера промолчал. Источник —
новая таблица `agent_run` (миграция `packages/db/drizzle/0088_agent_run.sql`), в которую рантайм
агентов пишет одну строку после каждого прогона — навыка по расписанию, порученной задачи, ручного
запуска с деки навыков и системного монитора.

### Доска рутин `/crons`

`GET /routines/board` — все маршруты `/routines/*` (в т. ч. GET) требуют сервисный токен: на
контроллере висит `RoutinesTokenGuard`, копия `DocsTokenGuard`, а не глобальный `ServiceTokenGuard`,
который чтение пропускает анонимно (в `reason`/`action`/`review` журнала — содержательный пересказ
работы агентов, открывать его без токена нельзя). Панель `apps/cc` поэтому ходит туда через
`getWithToken`, а не обычный `get`.

Что на экране (`apps/cc/src/app/crons/page.tsx`, пункт «Рутины» в группе SYSTEM навигации):

- **Снимок расписаний** — рантайм пушит его через `PUT /routines/snapshot` при каждой перечитке
  карточек (`reconcileSchedules()`) и после заведения мониторов; Core хранит одну строку
  (`agent_runtime_snapshot`, key `schedules`) и сам считает «следующий запуск» через `croner`
  (Asia/Tashkent) в момент запроса — снимок не устаревает вместе с расписанием. Возраст снимка
  старше **900 секунд (15 минут)** — доска показывает «агенты не отчитывались N мин»: это чаще всего
  означает, что контейнер `mydon-agents` упал или не пересобрался.
- **Тумблеры паузы** — те же `AGENTS_SCHEDULES_PAUSED`/`AGENTS_TASKS_PAUSED` из `system_config`, что
  на `/system`; источник истины для доски — сам `system_config`, а не то, что было в снимке на момент
  его отправки.
- **«Ближайшие 24 ч»** — все occurrences в окне `[now, now+24h]` (включая повторные, например
  `*/3`), максимум 200 суммарно, сгруппированы «сегодня/завтра»; строка ведёт на `/flows?agent=…`.
  Тот же список первыми пятью строками — виджет «Ближайшие 24 ч» на главной (`/mydon`), через
  `core.cronBoard()` в `try/catch`: сбой не рушит страницу, блок просто не рисуется.
- **«Все расписания»** — таблица заданий, включая отключённые (`disabledReason`: навык не подключён,
  LLM-маршрут выключен, `<NAME>_CRON=off` в `.env`, нет учётки OurVend) и приостановленные (серым).
  Мониторы паузе расписаний **не подчиняются** — синк источников не должен вставать вместе с
  навыками агентов.

### Журнал прогонов

Таблица `agent_run` + `agent_runtime_snapshot` — та же миграция `0088`. Пишет **рантайм**
(`apps/agents`), а не Core: одна точка записи что для legacy cron-колбэка, что для задачи из
`agent-schedule`, что для деки и мониторов. `POST /routines/runs` идемпотентен по `request_key`
(уникальный столбец) — повтор с тем же ключом обновляет только поля исхода и отвечает
`created: false`, ничего не дублирует. Запись — best effort (`apps/agents/src/run-journal.ts`,
`reportRun`): ошибка записи гасится в `console.warn`, сам прогон навыка не страдает.

`GET /routines/runs?agent=&skill=&outcome=&limit=` (лимит ≤ 200, по умолчанию 50) — сырой список;
`GET /routines/runs/last?agent=&skill=` — последний прогон одного задания, им пользуются хук
`source_fresh` и дека навыков.

**Триггер записи** (`trigger: "cron" | "task" | "manual"`, ruling волны R): задача, которую Core
завело из планового тика крона (`source = agent-schedule`), журналируется с `trigger: "cron"`, а не
`"task"`, как в первой редакции спеки — она такое же плановое срабатывание, только исполненное
durable-путём вместо in-process, и тихие часы вместе с подписью фазы «Триггер» плейбэка обязаны
читаться одинаково для обоих способов запуска одного и того же расписания. Задача, поручённая
владельцем напрямую, — `"task"`; запуск кнопкой с деки навыков (`/skills`) — `"manual"`.

**Мониторы под журналом** (`apps/agents/src/monitors.ts`, `journaledMonitor`/`scheduleMonitor`):
шесть системных env-cron мониторов — `ourvend:sync`, `ourvend:accounting`, `coffee:monitor`,
`maintenance:monitor`, `globerent:monitor`, `fx:refresh` — журналируются как `agent_name = "system"`,
`skill = <имя монитора>`, `trigger: "cron"`; `request_key = monitor:<name>:<cron>:<occurrence ISO>`.

### Плейбэк `/flows`

`GET /routines/flows?agent=&skill=&outcome=&limit=` — список прогонов (обёртка над `agent_run`, те
же фильтры и лимит, что у журнала); `GET /routines/flows/:id` — плейбэк одного прогона. Панель
(`apps/cc/src/app/flows/page.tsx`, пункт «Прогоны» в SYSTEM) рисует полосу из **шести фаз, всегда в
одном порядке**: `trigger → skill → proposal → approval → execution → delivery`, каждая со
статусом `ok | warn | fail | skip`. То, что не нашли, — фаза `skip`, а не выдуманное состояние.
Источники фаз, кроме самого `agent_run`: `agent_skill_catalog` (executor/tier навыка), `approval`,
`task`/`task_agent_execution`, `outbox_delivery`, `event` (окно `[started_at − 1 с; finished_at + 1
с]`, источник `agent:<name>`) и `audit_log` (тем же окном, по `target` задачи и согласования: у
задачи с несколькими попытками `target` один на все) — новых столбцов в существующих таблицах для
этого нет.
Под полосой фаз — лента: события шины и записи аудита одной колонкой по времени
(`mergeRunTimeline`, `packages/shared/src/run-timeline.ts` — одна реализация на панель и Core).
Лента — **события агента в окне прогона, а не события этого прогона**: привязки события к прогону в
схеме нет, выбор идёт по `source=agent:<имя>` и времени, поэтому у агента с одновременно работающими
cron-колбэком и task-worker в ленту попадают строки соседнего прогона (панель подписывает это прямо).

### Хуки паспорта

Необязательный раздел `hooks:` в `config.yaml` агента (пример — закомментированный блок в
`apps/agents/agents/_template/config.yaml`):

```yaml
hooks:
  pre_run:
    - kind: source_fresh
      run: system/ourvend:sync
      max_age_hours: 6
    - kind: quiet_hours
      from: "23:00"
      to: "07:00"
  post_run:
    - kind: coach_lite
```

Реализация — реестр по `kind` в `apps/agents/src/hooks.ts`; `runSkill` (`apps/agents/src/runner.ts`)
вызывает `runPreRunHooks` перед резолвом навыка и `runPostRunHooks` после результата.

**Kinds этой волны:**

- **`source_fresh`** (`pre_run`) — источник `run: agent/skill` (или `system/<монитор>`) должен иметь
  последний прогон с исходом `executed` не старше `max_age_hours`; нет прогона, исход не `executed`,
  возраст не считается или журнал недоступен — во всех случаях **блок** (fail closed: ложный пропуск
  дешевле действия на протухших данных).
- **`quiet_hours`** (`pre_run`) — интервал `HH:MM–HH:MM` по Ташкенту, допускает переход через
  полночь; ручной запуск (`trigger: "manual"`) хук не проверяет.
- **`coach_lite`** (`post_run`) — без LLM, по последним прогонам того же задания (текущий + 5
  истории): 3 `skipped:llm_failed|llm_invalid_output` подряд → «LLM-маршрут падает N прогонов подряд
  — проверь ключ/модель в /system»; 5 `skipped:no_signal` подряд → «пять тихих прогонов подряд —
  расписание можно проредить»; 3 `approval_requested` подряд → «три предложения подряд ждут решения»;
  `failed` дважды подряд → «сбой второй раз подряд: <reason>». Строка пишется в поле `review` той же
  записи журнала.

**Что блокирует.** Неизвестный `kind` в `pre_run` **блокирует навык** — не угадываем: журнал получает
`skipReason: "hook_blocked"` и `hook: <kind>`, доска и плейбэк показывают его как обычную причину
пропуска. Неизвестный `kind` в `post_run` — только предупреждение в лог и находка `check:passports`,
сам прогон не страдает.

**Область действия `pre_run`** (ruling волны R, §4.4 спеки): проверяется **только** у прогонов по
расписанию — `trigger === "cron"` (и легаси cron-колбэк, и durable-задача из `agent-schedule`;
отсутствующий `trigger` тоже считается `cron` — консервативно). Поручённая владельцем задача
(`task`) и запуск с деки навыков (`manual`) идут **мимо** `pre_run` — владелец попросил сам, и
«не запускал: тихие часы» закрыло бы его поручение как выполненное без причины. Задача в
task-режиме **с уже сохранённым checkpoint** (takeover) тоже мимо `pre_run` — хук стережёт СТАРТ
прогона, а не возобновление уже (возможно оплаченной) работы. Если хук блокирует именно плановую
durable-задачу, рантайм сначала сохраняет checkpoint `{ kind: "no_signal" }`, затем коммитит исход
`no_signal` — Core не знает kind `hook_blocked` и до расширения `commitPayload` (вне среза) закрывает
occurrence этим способом; в самом журнале (`agent_run`) исход остаётся точным: `hook_blocked` +
имя хука.

**Встроенные проверки** (не хуки, дублировать их в паспорте не нужно — они всегда в рантайме):
пауза (`AGENTS_SCHEDULES_PAUSED`/`AGENTS_TASKS_PAUSED`), статус агента, дневной бюджет
(`skipReason: budget_denied`), потолок действий (`capped`), дельта-память (`no_change`),
LLM-ledger (`ledger_unavailable`). Доска и плейбэк показывают их как обычные причины пропуска —
словарь `RUN_SKIP_REASONS` (`packages/shared/src/agent-runs.ts`, 12 причин, включая `hook_blocked`)
общий для Core, панели и (позже) бота.

**Проверка паспортов.** `pnpm --filter @mydon/agents check:passports` читает `hooks:` настоящим
YAML-разбором (`parseYaml` из пакета `yaml` — местный мини-парсер вложенные списки не понимает) и
находит: неизвестный `kind`, `max_age_hours ≤ 0`, `run` не вида `agent/skill`, `from`/`to` не
`HH:MM`. Хуки лежат в карточке агента (`agent.hooks` jsonb, та же миграция `0088`, default
`{}`) — блок «Хуки прогона» в `/agents/<имя>` показывает их только на чтение.

**Хук паспорта сам собой в существующую карточку НЕ попадёт.** `POST /agents/seed` идемпотентен:
он заводит новых агентов и пропускает существующих (иначе обновление системы затирало бы правки
владельца в панели), а рантайм грузит агентов ИЗ базы. Значит `hooks:`, дописанный в паспорт уже
заведённого агента, останется только в файле — то есть нигде. Для всех 12 карточек, заведённых до
волны R, хуки доносит `node tools/apply-passport-fields.mjs` (поле `hooks` в списке «заполняются,
если в базе пусто»; `--dry-run` покажет, что уйдёт, `--overwrite=hooks` перепишет заданное) — либо
`PATCH /agents/:name` с сервисным токеном вручную. Проверка — блок «Хуки прогона» в карточке.

### Проверка на проде

`GET /routines/board` с токеном → `snapshot.stale=false`, `jobs` содержит все шесть мониторов и
задания активных агентов. После первого тика любого задания — строка в
`GET /routines/runs?agent=system` и рабочий плейбэк (`GET /routines/flows/:id` → 6 фаз). `/crons`,
`/flows`, `/mydon` → 200, на `/mydon` виден блок «Ближайшие 24 ч». Анонимный `GET /routines/board`
(без `x-service-token`) → 401; `POST /routines/runs` с битым `outcome` → 400.

владельца и CLI `mydon` для терминала/скриптов, поверх ОДНОГО клиента Core
(`apps/mcp/src/core-client.ts`, Р-1: третья копия fetch поверх Core не
заводится). Полное описание MCP-инструментов, туннеля и переменных
окружения — `docs/MCP.md`; здесь — только CLI и конвенция сухого прогона.

### Команды

`apps/mcp/src/cli.ts`, одиннадцать команд (`COMMANDS`): `inbox`, `tasks`,
`task <id>`, `task-create --title … [--yes]`, `events`, `runs`, `kb <path>`,
`search <q>`, `briefing`, `agents`, `decide <id> approved|rejected --yes`.
Читающие печатают тот же компактный текст, что видит модель через MCP
(общие форматтеры `apps/mcp/src/format.ts`); флаг `--json` у любой команды
печатает сырой ответ Core вместо текста — для скриптов и `| jq`. Неизвестный
флаг всегда ошибка (`apps/mcp/src/args.ts`, `parseArgs`) — не молчаливое
игнорирование, как в `argv.includes(...)` у старых `tools/*.mjs`; опечатка
рядом с известным флагом (расстояние Левенштейна ≤ 2) получает подсказку
«возможно, вы имели в виду --…». Известный флаг БЕЗ значения (`--status`
перед другим флагом или `--status=`) — тоже ошибка использования, а не
«фильтр не задан»: тихо отброшенный отбор дал бы правдоподобный ответ на
другой вопрос.

Задача, созданная командой `task-create`, приходит в Core с источником
`mydon-cli` (у инструмента MCP `task_create` — `mcp`): в карточке видно,
завёл её владелец из терминала или модель.

Коды возврата: `0` — успех (в том числе «напечатано намерение, Core не
звали»), `1` — Core ответил ошибкой (переведённый текст Р-9, без токена),
`2` — ошибка использования (не хватает аргумента, неизвестный флаг/команда).
Успех уходит в stdout, ошибка — в stderr, поэтому `mydon inbox --json | jq`
не увидит сообщение об ошибке вперемешку с данными.

### Конвенция `--yes` (Р-7)

У всех команд, меняющих мир (`task-create`, `decide`), обязателен явный
флаг `--yes`. Без него команда печатает намерение («Будет создана задача
«…» владелец: …») и завершается кодом `0`, ни разу не обратившись к Core.
Это единая конвенция сухого прогона для новых скриптов CLI/`apps/mcp` —
существующие 25 скриптов `tools/*.mjs` при этом НЕ переписываются (у них
своя, менее строгая проверка через `argv.includes(...)`), но новые скрипты
пишутся по этому правилу: сухой прогон по умолчанию, явный `--yes` для
реального действия.

### Примеры

```sh
mydon inbox                                   # то же, что видно на /inbox
mydon tasks --status todo --owner Бехруз
mydon task-create --title "Проверить бункер" --owner-kind human --owner Бехруз
                                               # без --yes — только печатает намерение
mydon task-create --title "…" --owner-kind human --owner Бехруз --yes
mydon decide <id> approved --yes
mydon events --source agent:vendhub-ops --limit 20
mydon kb docs/MCP.md
```

## Как читать состояние агентов и приложений (волна A2, 06.09)

Волна A2 (`docs/decisions/2026-09-06-wave-a2-faces.md`, спека
`docs/superpowers/specs/2026-09-06-wave-a2-faces-design.md`) даёт владельцу два ответа с одного
взгляда: кто из агентов сейчас работает и почему остальные молчат (`GET /agents/status`, сетка на
`/mydon`, карточка `/agents/<имя>`), и что происходит с источниками — OurVend, курсом, Notion,
Telegram-ботом, моделями (`GET /apps/health`, панель `/apps`). Оба маршрута читающие, но
ЗАКРЫТЫ СЕРВИСНЫМ ТОКЕНОМ (`ReadTokenGuard`, круг починок C-1): глобальный гард Core пропускает
`GET`, а эти два печатают наружу `agent_run.reason` — то самое поле, ради которого волна R закрыла
журнал прогонов. Отдают только состояния и человеческие причины — ни токенов, ни payload событий,
ни строк подключения. Панель ходит в них `getWithToken`; смоук — с заголовком (и отдельно
проверяет, что без него оба отвечают 401).

### Четыре состояния агента

`working | blocked | paused | idle` — считает Core (`apps/core/src/agents/agent-state.ts`,
`computeAgentState`), панель их только показывает: третья копия правила лизы (наравне с worker и
Core) разошлась бы при следующей правке.

- **`working`** — есть задача этого агента с живым claim: `agentRunClaimedAt` свежее лизы
  `TasksService.AGENT_RUN_LEASE_MS` (15 минут). Источник «прямо сейчас» — задача, а не журнал
  прогонов `agent_run`: в журнале обе отметки времени пишутся только постфактум, по завершении.
- **`blocked`** — Core остановил исполнение и записал причину (`agentExecutionBlockedAt`/
  `agentExecutionBlockedReason`), причём затык перекрывает `working`, только если относится к
  ТЕКУЩЕЙ работе — та же задача, или отметка не старше живого claim, или живой работы нет вовсе.
  Затык недельной давности, пока агент выполняет другую задачу прямо сейчас, `working` не
  перекрывает: экран показывает работу, а старый затык уходит хвостом в причину.
- **`paused`** — агент не может взять работу: архив, системная пауза задач
  (`AGENTS_TASKS_PAUSED`) или паспортный статус, отличный от `active` (`paused`/`draft`/
  `deprecated`). Причина называет источник словами («агент выключен в карточке», «задачи агентов
  на паузе (это настройка системы, а не агента)»), чтобы было видно, что именно снимать.
- **`idle`** — всё остальное: задач нет, последний прогон прошёл или тихо пропущен (повода не
  было), либо агент ещё ни разу не запускался. «Молчит» и «работает, но без результата» — одно и
  то же состояние `idle`; причина в `lastRun.reason`/`skipReason` показывает, что именно случилось.
  Сетка на `/mydon` (`apps/cc/src/components/agent-grid.tsx`) отдельно подсвечивает `idle`,
  вызванный ПОЛОМКОЙ (`llm_failed`, `ledger_unavailable`, `execution_unknown`, `hook_blocked`) тоном
  предупреждения — иначе сломанный маршрут к модели неделю выглядел бы обычным спокойным молчанием
  рядом с «повода нет»/«без изменений».

**Порядок правил, которым Core вычисляет состояние: архив → системная пауза задач → паспортная
пауза → затык (если относится к текущей работе) → работает → молчит.** Занятость стоит НИЖЕ пауз
намеренно (Р-2 решения волны A2): при `AGENTS_TASKS_PAUSED=1` агент не может взять задачу, и
«работает» было бы прямой ложью на самом заметном экране, даже если формально у него ещё висит
старый claim.

### Три состояния источника — и «не оценить» не похоже на «в порядке»

`ok | bad | unknown` — считает Core (`apps/core/src/apps/apps-health.ts`), панель (`/apps`) их
только показывает словом и своим классом лампы: `unknown` не получает зелёного ни в одной теме.

- **`ok`** — был успешный прогон в ожидаемом окне (или сверка сошлась, или бот ответил недавно).
- **`bad`** — последний прогон `failed`, серия отказов, застой (данные протухли), вставшая
  очередь доставки или сорванный дневной бюджет моделей.
- **`unknown`** — источник, о котором НЕЧЕГО сказать: прогонов нет вовсе, монитор выключен,
  учётной записи нет, снимок расписаний ещё не публиковался, очередь доставки пуста. **Ноль
  прогонов — это `unknown`, а не `ok`.** Причина: молчание и здоровье выглядят одинаково спокойно
  сегодня, но означают разное. Выключенный монитор не падает и не жалуется — у него просто нет
  прогонов, «ошибок нет» о нём было бы правдой формы и ложью смысла; `failedStreak = 0` держится
  вечно, если крон вообще перестал запускаться, а не только если он перестал падать. По той же
  причине источник, чьи доставки ВСЕ в статусе `skipped` (Notion не настроен), не зелёная строка
  «доставлено 0» — это `unknown` «источник не настроен»: раньше здесь была найденная ревью ошибка
  (Critical, задача 3 этой волны).
- Вставшая очередь доставки (Notion) краснеет по **возрасту самой старой неразобранной строки**
  (`OUTBOX_STUCK_MS`, час), а не по статусу — диспетчер не падает, а молчит, и без этого правила
  «в очереди 500» спокойно зеленело бы месяцами.

Панель `/apps` (`apps/cc/src/app/apps/page.tsx`) делит источники на два раздела по природе связи
(Р-3): «Снаружи» — то, что реально ходит в чужую систему (`ourvend:sync`, `ourvend:accounting`,
`fx:refresh`, Notion, Telegram-бот, модели); «Внутренние мониторы» — `coffee:monitor`,
`maintenance:monitor`, `globerent:monitor`, которые читают только Core, и их «здоровье» — это
здоровье данных, а не связи со внешним миром. Смешение разделов обещало бы связь, которой нет.

### Почему системная пауза перекрывает занятость и как её снять

Пока `AGENTS_TASKS_PAUSED=1` (дефолт новой установки), ни один агент не может взять задачу — и
сетка на `/mydon` показывает не двенадцать спокойных плиток, а заметную строку «Задачи агентов на
паузе. Это настройка системы, а не состояние агентов». То же для `AGENTS_SCHEDULES_PAUSED` в части
расписаний. Снять — тумблером в панели `Система · Активация` (`/system`) или `.env` (см. «Карта
тумблеров» выше); правки через панель перекрывают `.env` без пересборки.

**Оба тумблера читаются «отказом в сторону паузы» (постановление ветки волны A2):** нет ключа в
`system_config`, значение не строго `"0"` — считается, что пауза включена. Дефолт обоих тумблеров в
`config-spec` равен `"1"`, и рубильник всего парка обязан ломаться в «выключено» — пустой или
чужой ответ настроек не должен нарисовать двенадцать работающих агентов там, где задачи реально
стоят. Доска рутин (`/crons`, `apps/core/src/routines/board.ts`) приведена к тому же правилу, чтобы
`/agents/status` и `/crons` не расходились в ответе «парк на паузе?» — расхождение было найдено в
ревью этой волны сразу после первого прохода фикса.

### Где смотреть причину

- **Сетка `/mydon`** и плитка агента — `row.reason`, одна фраза под именем.
- **Карточка `/agents/<имя>`** — состояние с причиной в шапке (тот же `GET /agents/status`, тот же
  словарь состояний, что и в сетке — второй словарь разошёлся бы с первым на первой же правке).
- **Панель `/apps`** — `summary` в строке источника (что известно) и `detail` (цитата источника:
  итог прогона, ошибка доставки — текстом, без разметки). Текст СЕРВЕРНОГО исключения (например,
  обрыв соединения с Postgres) наружу никогда не едет: строка получает нейтральную причину
  («источник не отвечает — оценить нечем»), подробность уходит только в журнал Core — маршрут
  читается анонимно, а сообщение драйвера БД может нести хост и пользователя.
- **Журнал прогонов `/flows`** (волна R) — для истории: `agent_run.reason`/`skip_reason` за
  прошлые заходы, если причины на сетке недостаточно.

## Preflight перед включением Bot / CC / Documents

Эти три поверхности используют `MYDON_ASSISTANT_MODEL` и Anthropic. Перед
rollout миграции проверь значение ключа в production `.env`:

- пустое значение возьмёт штатную модель, для которой миграция уже содержит
  цену;
- непустое значение должно иметь действующую exact/dated строку
  `provider=anthropic` в `llm_model_price`;
- старый произвольный override (например, модель 4.x без строки каталога) после
  включения ledger будет намеренно отклонён fail-closed до вызова провайдера.

Сначала применить миграцию и проверить каталог, затем перезапускать
`mydon-core`, Bot и CC. Не добавляй «примерную» цену только ради прохождения
проверки: тариф должен быть отдельной версионированной миграцией.

## Сценарий 2 — включить семантическую память (RAG)

1. Поднять OpenAI-совместимый `/embeddings` (локальная модель в Tailscale или
   облачный endpoint).
2. В `.env`:

   ```
   EMBED_BASE_URL=http://<tailscale-host>:<port>
   EMBED_PRICE_PROVIDER_ID=openai        # exact llm_model_price.provider; не URL/секрет
   EMBED_MODEL=text-embedding-3-small     # или своя
   # EMBED_API_KEY=...                     # если endpoint требует
   EMBED_BILLING_MODE=metered             # default; local только для локальной модели
   ```

   Для metered-модели нужна действующая строка с
   `provider=$EMBED_PRICE_PROVIDER_ID` в `llm_model_price`, по тем же правилам,
   что в сценарии 1б. Без ID embedding блокируется до provider; при
   `EMBED_BILLING_MODE=local` ID можно оставить пустым.

Что оживает: `assess-ideas` перед оценкой **вспоминает похожие уже разобранные
идеи** и просит модель не повторять их, а после — запоминает разобранные посты.
Хранение — в журнале Core (переживает рестарт). Векторы разной длины/битые
считаются несовпадением (0) — память не «галлюцинирует» совпадения.

Граница инъекций сохранена: пересказ прошлых постов — тоже внешний текст, идёт в
**недоверенный** блок под маркером, доверенная инструкция лишь просит не
повторять.

## Сценарий 3 — самоулучшение (coach) и применение правок

Петля: coach судит последнее действие агента по рубрике → при «improve»
предлагает правку `SKILL.md` (SEARCH/REPLACE diff) → владелец одобряет →
правка ложится git-коммитом.

- **Судья** (`coach-review`) оживает вместе с мозгом (Сценарий 1). `coach-agent`
  уже `active`, расписание еженедельное. Правка НЕ применяется сама — приходит
  предложением в очередь (diff в фактах). Безопасность 1–2 по рубрике → эскалация
  без правки. Судья не судит сам себя.
- **Применение** одобренной правки — отдельная деливерейт-операция **там, где
  есть репо и git** (обслуживающий скрипт / CI / машина владельца), НЕ в
  эфемерном проде:
  ```
  pnpm --filter @mydon/agents coach:apply -- <агент>/skills/<навык>.md <файл-с-diff>
  ```
  Инварианты (все проверяются): path-guard (только `<агент>/skills/<навык>.md`
  известного агента), каждый блок diff указывает на тот же файл, SEARCH
  символ-в-символ, коммит только при успехе, git-откат. Правится **только**
  `SKILL.md` — никогда код/config/ROLE/факты.

## Проверка «включилось ли»

При старте `apps/agents` печатает позы (posture) LLM-пути, бюджета и coach —
видно, что активно, а что спит. Если тумблер задан, но навык молчит, порядок
проверки: (1) `LLM_ENABLED=1`, (2) выбран рабочий `openai-api`, а не
заблокированный `codex-subscription`, (3) `LLM_API_KEY` задан только на сервере,
(4) `ideaChannels`/`webSources` в паспорте не пусты, (5) канал/сайт реально
читается, (6) нужный контур снят с паузы:
`AGENTS_SCHEDULES_PAUSED=0` для cron или `AGENTS_TASKS_PAUSED=0` для порученной задачи,
(7) pricing profile существует,
расчётный reserve не превышает `$3`, и Core разрешает его до provider.

Ничего не задано → это не поломка: агенты работают детерминированно, очередь
остаётся сигналом, а не лентой.

## Durable provider result, retrieval snapshot, checkpoint и Notion outbox (миграции 0076–0079)

Этот контур действует только для **задачи, порученной агенту через Core**. После
claim worker сначала создаёт в Core `active` execution: фиксируются исходный
task-input hash (`title` + `description` + `domain`), versioned workflow plan и
устойчивый `executionAttemptId`.

Для навыка с волатильным read-only retrieval миграция 0079 добавляет ещё
одну границу до provider dispatch: first-write-wins `inputSnapshot` в той же
execution. Core канонизирует публичный JSON, ограничивает его 64 KiB,
хэширует и на exact replay возвращает те же evidence; иной payload для того
же execution отклоняется. `solution-scout` сохраняет так `solution-search-v1`
после fixed-host GitHub retrieval и до единственного paid ranking. Падение в этом
окне больше не повторяет поиск и не меняет prompt перед повтором.

Каждый metered chat/embedding шаг получает отдельный durable job. До HTTP-вызова
Core сохраняет точный provider JSON без auth/secrets и выдаёт один dispatch
token; после ответа одной транзакцией сохраняет immutable result и settlement
денежного резерва. Exact payload очищается в terminal state, а operation/result
hash остаются для аудита.

Plan привязывает каждый metered шаг к secret-free профилю маршрута вида
`openai-chat-completions:sha256:<hash>` или
`openai-embeddings:sha256:<hash>`. Hash считается от canonical effective
HTTP(S) base URL; raw URL не попадает в Core. Credentials, query, fragment и
не-HTTP(S) URL запрещены. Если после start изменился endpoint, provider,
adapter, billing mode или gateway, Agents не обращается к провайдеру и
освобождает claim с причиной `workflow_changed`. Core сохраняет стабильный
durable block; автоматический takeover его не обходит.

Если worker упал **после** durable complete, следующий claim получает сохранённый
result и продолжает тот же workflow без повторной оплаты. Поздний ответ вправе
сохранить worker старой generation по исходному dispatch token, но его старый
`runId` всё равно не пройдёт checkpoint/commit fence и не применит эффекты
задачи. Отказ бюджета на позднем шаге тоже не стирает уже готовые ранние шаги:
на новых ташкентских сутках повторяется только server-side authorization этого
job, а не provider-вызовы законченных job.

После вычисления checkpoint endpoint хранит неизменяемый результат навыка
(`proposal` либо `no_signal`), manifest всех provider jobs, его hash, исходный
task-input hash и execution plan hash. Если worker упал или lease перехватил
другой worker, следующий claim получает этот checkpoint: навык и LLM повторно
не запускаются.

Следующий шаг — один атомарный commit в PostgreSQL. Fence текущей generation,
результат и статус задачи, применимые event/memory/approval и intent публикации
отчёта в Notion либо фиксируются вместе, либо не фиксируется ничего. Точный
повтор с тем же payload возвращает прежний результат; другой payload для того
же `executionAttemptId` считается конфликтом. Notion вызывается только после
commit отдельным dispatcher, поэтому сбой Notion не откатывает выполненную
задачу и не теряет её внутренний результат.

Честная граница гарантии теперь раньше checkpoint: Core выдаёт не более одного
application dispatch grant на physical job, а принятый Core result повторно
читается без provider. Это всё ещё **не exactly-once**: без provider idempotency
или status API остаётся окно `dispatch grant → wire → durable complete`. Если
процесс умер в нём, job становится `unknown`; автоматический dispatch/fallback
запрещён, даже если пакет фактически не успел уйти. Late result с тем же token
может закрыть unknown, иначе дальнейшую оплату разрешает только владелец после
сверки.

В task-scoped durable slice пока **не входят** cron-запуски навыков, Assistant,
Documents и доставка Telegram. Local/subscription task gateways также не
получают USD-job: v3 покрывает только metered HTTP chat/embedding. Общий
`LLM_ENABLED` и суточный ledger при этом действуют на все metered-reserve Core,
но у остальных поверхностей нет task-scoped provider result из 0077. Notion
report — единственный внешний destination outbox 0076; наличие таблиц не
означает, что Telegram или документы уже получили durable delivery.

### Состояния Notion outbox

| Состояние     | Значение                                                                              | Действие оператора                                                                                                                          |
| ------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `pending`     | Intent создан в той же транзакции, что outcome задачи                                 | Ничего не менять: dispatcher заберёт его по FIFO                                                                                            |
| `dispatching` | Core выдал delivery по lease **до** запроса в Notion                                  | До 15 минут ждать завершения; если старше — запустить/восстановить один dispatcher и затем разбирать как `unknown`, не возвращать в pending |
| `sent`        | Notion подтвердил создание, `provider_ref` сохранён                                   | Ничего                                                                                                                                      |
| `skipped`     | Notion не настроен; внутренний outcome задачи уже сохранён                            | Настроить Notion для будущих delivery; этот intent автоматически не повторяется                                                             |
| `unknown`     | Timeout/обрыв, `409`, `5xx` либо просроченный `dispatching`: страница могла создаться | Вручную искать отчёт в Notion по заголовку и времени; не найдено — владелец отдельно решает о новой доставке, принимая риск дубля           |
| `dead`        | Явный `400/401/403/404`, исчерпаны bounded `429` retry или невалидный payload         | Проверить `last_error`, исправить причину и создавать только новую осознанную delivery, не переписывать старую строку                       |

Просроченный `dispatching` при следующем claim переводится в `unknown`, а не
обратно в `pending`: Notion create не имеет доказанной exactly-once
идемпотентности. Только `429` повторяется до двух раз внутри того же
claim с учётом `Retry-After`: такой ответ явно отклонил запрос. Для разбора
смотреть строки и логи вместе:

```bash
/opt/backups/db_access.sh query "
select id, key, status, attempts, claimed_at, completed_at, provider_ref, last_error
  from outbox_delivery
 where destination = 'notion-report'
   and status in ('dispatching', 'unknown', 'dead')
 order by created_at"
docker logs --since 30m mydon-agents 2>&1 | grep -i 'notion\|outbox'
```

Нельзя чинить инцидент прямым `UPDATE ... status='pending'`: это стирает
неоднозначность и может создать вторую страницу. Старую строку оставляют как
аудит; повтор — только отдельное решение владельца после сверки Notion.

## Если задача durable-заблокирована

Причина видна в карточке и `agent_execution_blocked_reason`. Block возникает,
если durable job стал `unknown`, exact operation/result hash не совпал, после
start/checkpoint изменили задачу или plan, владелец вернул committed-работу на
redo, runtime route/config разошёлся с plan (`workflow_changed`) либо у агента
нет подходящего навыка. Автоматика намеренно не вращает execution attempt: это
могло бы повторить оплату или применить устаревший результат. Для
`workflow_changed` owner retry всегда оставляет старый attempt для аудита и
создаёт новый с актуальным route profile, даже когда его jobs уже terminal.

1. При первичной настройке создать отдельный секрет, например
   `openssl rand -hex 32`, и записать его как `OWNER_ACTION_TOKEN` в `.env`.
   Он обязан отличаться от `SERVICE_TOKEN` (равенство блокируется кодом).
   Compose передаёт его только Core; не добавлять его Bot/Agents/CC.
2. Проверить `agent_execution_blocked_reason` задачи и финансовую строку
   `llm_spend` по `task:<taskId>:execution:`. Если прошлый результат уже был
   доставлен, retry не нужен.
3. Если владелец осознанно разрешает потенциально повторную оплату, вызвать:

   ```sh
   curl -X POST "http://127.0.0.1:3001/tasks/<task-id>/agent-run/retry" \
     -H "x-service-token: $SERVICE_TOKEN" \
     -H "x-owner-action-token: $OWNER_ACTION_TOKEN"
   ```

Маршрут fail-closed при пустом owner token и пишет
`task.agent_execution.retry` в audit log. Передавать `actor:"owner"` в JSON
недостаточно и больше не поддерживается.
