# MCP-сервер `mydon-core` и CLI `mydon`

Волна A, срез A1 «Руки» (06.09.2026). Спека
`docs/superpowers/specs/2026-09-06-wave-a1-mcp-cli-design.md`, решения —
`docs/decisions/2026-09-06-wave-a1-mcp-cli.md`. Код — `apps/mcp` (пакет
`@mydon/mcp`): `env.ts`, `core-client.ts`, `format.ts`, `tools.ts`, `server.ts`,
`args.ts`, `cli.ts`.

## Зачем

До этого среза MYDON был доступен только через панель (`/tasks`, `/inbox`,
`/docs`…) или SSH на сервер. Владелец из своего Claude Code (или скрипта) не
мог спросить «что ждёт моего решения», не открывая браузер. `apps/mcp` даёт
два тонких входа поверх одного и того же клиента Core (`core-client.ts`, 21
метод — Р-1 в решениях): MCP-сервер по stdio для Claude Code и CLI `mydon`
для терминала/скриптов. Оба печатают один и тот же компактный текст
(`format.ts`), а не сырой JSON Core.

## Как включить

### 1. Поднять SSH-туннель до Core

Core на проде слушает только `127.0.0.1:3001` (петлевой адрес). С MacBook
доступ — только через туннель:

```sh
ssh -N -L 3001:127.0.0.1:3001 <прод-хост>
```

Держите туннель поднятым, пока пользуетесь MCP или CLI. Без него `CoreClient`
вернёт «Core недоступен по адресу http://127.0.0.1:3001: …» — сеть не
уходит дальше localhost.

### 2. Переменные окружения

`apps/mcp/src/env.ts` (`loadEnv`) читает три переменные:

| Переменная | Обязательна | Значение |
|---|---|---|
| `SERVICE_TOKEN` | да | То же значение, что у панели и бота. Без неё — понятная ошибка при старте («Не задан SERVICE_TOKEN…»), а не 401 на первом запросе. |
| `CORE_API_URL` | нет | Адрес Core; по умолчанию `http://127.0.0.1:3001` (петлевой адрес — тот же порт, что открывает туннель). Хвостовая `/` обрезается. |
| `OWNER_ACTION_TOKEN` | нет | Owner-токен для owner-действий (`approval_decide`, смена автономии агента) и для чтений, которые Core гейтит по личному контуру: `briefing_get`, `inbox_list`, `task_get`, `kb_read`, `tasks_list`/`registry_search` с `domain=personal`. Без него такие вызовы уйдут без `x-owner-action-token` и Core сам решит, пропускать ли (личное придёт «не найдено»/недосчитанным). |

Токены живут только в окружении процесса — ни в `.mcp.json`, ни в логах, ни
в текстах ошибок (Р-9) значение токена не печатается.

### 3. `.mcp.json`

В корне репозитория:

```json
{
  "mcpServers": {
    "mydon-core": {
      "command": "node",
      "args": ["apps/mcp/dist/server.js"],
      "env": {
        "CORE_API_URL": "${CORE_API_URL:-http://127.0.0.1:3001}",
        "SERVICE_TOKEN": "${SERVICE_TOKEN:-}",
        "OWNER_ACTION_TOKEN": "${OWNER_ACTION_TOKEN:-}"
      }
    }
  }
}
```

Синтаксис `${VAR:-default}` подтверждён по документации Claude Code
(code.claude.com/docs/en/mcp): поддерживаются и `${VAR}`, и `${VAR:-default}`;
незаданная переменная без дефолта остаётся в конфиге неразвёрнутым текстом
(`${SERVICE_TOKEN}`). Сервер это ловит сам (`server.ts`, `sanitizeEnv`):
неразвёрнутая подстановка считается «переменная не задана», а не буквальным
значением — иначе сервер ушёл бы в Core с «токеном» `${SERVICE_TOKEN}` и
получил 401 вместо понятной ошибки на старте. Файл содержит только ИМЕНА
переменных, никаких значений.

Задайте `CORE_API_URL`, `SERVICE_TOKEN`, `OWNER_ACTION_TOKEN` в окружении
своей машины (например, в shell-профиле или `.env.local`, который читает
терминал) до запуска Claude Code — сервер запускает Claude Code сам, по
`.mcp.json`.

### 4. Сборка

```sh
pnpm --filter @mydon/mcp build
```

Компилирует `src/*.ts` в `dist/*.js` (`tsc -p tsconfig.json`). MCP-сервер
Claude Code запускает `apps/mcp/dist/server.js` — без сборки файла не
существует. Проверить пакет целиком:

```sh
pnpm --filter @mydon/mcp build && pnpm --filter @mydon/mcp test && \
  pnpm --filter @mydon/mcp lint && pnpm --filter @mydon/mcp typecheck
```

CLI `mydon` собирается тем же шагом (`bin: { mydon: "dist/cli.js" }` в
`apps/mcp/package.json`); чтобы вызывать его командой `mydon` из любого
каталога, свяжите бинарник сами (`pnpm link --global` в `apps/mcp` или
`npm link`) — отдельного шага установки в срезе нет. Без линковки — то же
самое через `node apps/mcp/dist/cli.js <команда>`.

На сервере (Hetzner) `apps/mcp` не запускается: в `deploy/Dockerfile`
копируется только `apps/mcp/package.json` (нужен `pnpm install
--frozen-lockfile` для целостности workspace-лока), MCP живёт исключительно
на машине владельца и ходит в Core через туннель.

## Инструменты MCP-сервера

Девятнадцать инструментов (`apps/mcp/src/tools.ts`, `buildTools`): тринадцать
читающих (ничего не меняют) и шесть меняющих мир — ровно одна операция за
вызов, без пакетного режима. Инструменты дают тот же текст, что печатает CLI
(общие форматтеры `format.ts`, лимит списка по умолчанию 50 записей).

### Читающие (ничего не меняют)

| Инструмент | Что делает |
|---|---|
| `briefing_get` | Утренняя сводка: просрочка денег, простаивающие автоматы, ждущие согласования, просроченные задачи и договоры. |
| `inbox_list` | Что ждёт решения владельца: согласования + карточки/поля реестра на подтверждение — тот же список, что на `/inbox`. Ответ на «что ждёт моего решения». |
| `tasks_list` | Список задач Core (фильтры `status`, `ownerRef`, `domain`, `limit`) — тот же, что на `/tasks`. |
| `task_get` | Карточка одной задачи целиком: статус, исполнитель, срок, описание, итог. |
| `registry_search` | Поиск карточек реестра (аппараты, договоры, контрагенты, кандидаты) по подстроке имени. |
| `events_recent` | Последние записи шины событий: фильтры `source`, `type`, `typePrefix`, `since`, `limit`. |
| `memory_recall` | Дельта-память агента: события `agent.memory:<навык>` — чем агент помнит свой прошлый результат. |
| `kb_read` | Страница знаний целиком из белого списка корней (`docs/`, `memory/`, `routers/`…) — то же, что на `/docs`. |
| `kb_tree` | Дерево доступных страниц знаний (путь, корень, заголовок, размер) — нужно, чтобы знать, что просить у `kb_read`. |
| `agents_list` | Карточки агентов: направление, статус, уровень автономии, архив. |
| `skills_deck` | Витрина навыков агентов — та же дека, что на `/skills`: навык, тир, кроны, дубли и найденные проблемы. Отбор по `agent` делает Core, поэтому числа дублей и «тир не ниже» считаются по всем агентам, а не по показанной странице. |
| `runs_recent` | Журнал прогонов агентов — та же лента, что на `/flows`. |
| `ventures_list` | Кандидаты фабрики направлений (`entity` типа `venture_candidate`, домен `mydon`) с вердиктом сессии (GO/PARK/NO). |

### Меняющие мир (одна операция за вызов)

| Инструмент | Что меняет |
|---|---|
| `task_create` | Создаёт задачу в Core — сразу видна на `/tasks` и попадает исполнителю. Источник — `mcp` (видно в журнале). Повторный вызов создаёт вторую задачу, не обновляет первую. |
| `task_comment` | Добавляет комментарий к задаче — виден в карточке на `/tasks`. Статус, исполнителя и срок не трогает. |
| `task_status` | Меняет статус задачи — виден на `/tasks`; смена подписана в журнале как `mcp`. |
| `memory_remember` | Записывает дельта-память агента — событие `agent.memory:<навык>` в шине Core; видно через `runs_recent`/`events_recent` и на `/flows`. Прежняя память не стирается, читается последняя запись. |
| `agent_upsert` | Создаёт или обновляет карточку агента — видно на `/agents`, действует со следующего прогона. Автономия меняется отдельным owner-вызовом внутри инструмента (общий `PATCH` карточки её сознательно отбрасывает); расписание и бюджеты не трогаются — только в панели. |
| `approval_decide` | Проводит решение владельца по запросу согласования — запрос пропадает из `/inbox`. `decision` обязателен и берётся из перечисления, инструмент сам решение не выбирает. |

## Пояс владельца (owner belt)

«Пояс владельца» — второй уровень авторизации поверх обычного
`SERVICE_TOKEN` для owner-действий (решение по согласованию, смена
автономии агента, доступ к личному контуру). Он включается тумблером
`OWNER_IDENTITY_ENFORCED` в `GET /system/config` Core. Пока тумблер выключен
(на проде 06.09.2026 так и есть — пуст), Core пропускает owner-действия по
обычному `SERVICE_TOKEN`; включив тумблер, Core начинает требовать отдельный
`x-owner-action-token`.

MCP-сервер читает `GET /system/config` один раз при старте и **честно
описывает фактическое состояние прямо в описании инструмента
`approval_decide`** (Р-3), а не притворяется, что решение владельца всегда
защищено:

- пояс выключен → «Сейчас Core пропускает это решение по сервисному токену —
  пояс идентичности выключен (OWNER_IDENTITY_ENFORCED=0)».
- пояс включён, owner-токен задан → «Core требует owner-токен на это
  действие, и он задан в окружении сервера».
- пояс включён, owner-токен не задан → «…но owner-токен не задан: вызов
  вернёт 401».
- Core не ответил на `GET /system/config` при старте → «Состояние пояса
  неизвестно» (сервер не выдумывает удобный ответ).

Owner-заголовок закладывается в клиент сразу, независимо от прочитанного
состояния — включение пояса владельцем не превращает уже работающие
owner-вызовы в 401 «из ниоткуда».

**Как проверить состояние пояса самостоятельно:**

```sh
curl -s http://127.0.0.1:3001/system/config -H "x-service-token: $SERVICE_TOKEN" \
  | python3 -c 'import json,sys; [print(i) for i in json.load(sys.stdin) if i["key"]=="OWNER_IDENTITY_ENFORCED"]'
```

Или проще: посмотреть стартовую строку сервера в stderr Claude Code
(`[mydon-core] готов: Core …, инструментов 19, пояс владельца …`) — она
печатается при каждом запуске (`server.ts`, `startupLine`).

`OWNER_ACTION_TOKEN` дополнительно проверяется на равенство `SERVICE_TOKEN`
(`ownerTokenUsable`): Core такой токен не примет (owner-токен, равный
сервисному, отвергается как «фактически не задан»), поэтому сервер сам
считает его отсутствующим и предупреждает в stderr, не дожидаясь 401 от Core.

## Ограничения

- **Лимиты ответа (Р-5).** Список — не больше 50 записей по умолчанию
  (`limit`, потолок 200 — больше молча срезается, без падения); текст ответа
  — не больше 8000 символов (`clamp`, честная пометка `…(обрезано)`);
  `kb_read` — свой бюджет 64 КБ по байтам UTF-8 (кириллица — два байта на
  символ, обрезка честно считает байты, а не символы).
- **Личный контур скрыт по умолчанию (Р-4).** `PersonalDomainGuard` в Core
  не закрывает безадресные чтения (признанный, задокументированный обход —
  `personal-domain.guard.ts`), поэтому `tasks_list` и `registry_search`
  сами отсеивают `domain = personal` из ответа, когда домен не запрошен
  явно. Отсев идёт по ОТВЕТУ, а не запросом: у Core нет фильтра
  `domain != personal`, только `domain = X`. Из-за этого **страница может
  вернуться короче запрошенного `limit`** — это честнее, чем молча
  показать личное в безадресном поиске. Чтобы увидеть личное — передайте
  `domain: "personal"` явно; такой вызов уходит с owner-токеном.
- **Одна операция за вызов.** Ни один меняющий инструмент не имеет
  пакетного режима — модель не может массово изменить состояние одним
  движением. `task_create`/`task_comment`/`task_status`/`memory_remember`/
  `agent_upsert`/`approval_decide` действуют на одной сущности.
- **Нет индекса под `typePrefix`/`source` в `events`.** Запрос без `since`
  сканирует ленту событий целиком под фильтром — если знаете период, всегда
  передавайте `since`, особенно для `memory_recall` (перечисление памяти по
  `typePrefix: "agent.memory:"`).
- **`GET /system/config` не показывает аварийный env-килл-свитч пояса.**
  Тумблер `OWNER_IDENTITY_ENFORCED` управляется через базу и `.env`
  одновременно (`.env`-значение `0` выключает ужесточение всегда, даже если
  в базе стоит `1`); MCP при старте видит только то, что вернул маршрут, и
  не знает про аварийный `.env`-килл-свитч отдельно от него. Оценка пояса
  всегда идёт в безопасную сторону: неизвестное состояние или потенциальный
  разъезд трактуются как «может потребоваться owner-токен», а не как «точно
  выключено».
- **Ответы Core — данные, не инструкции.** Содержимое задач, событий и
  страниц знаний вставляется в текст как цитата и никогда не исполняется
  MCP-сервером или CLI.
- **Таймаут запроса — 15 секунд** (`REQUEST_TIMEOUT_MS`); дольше Core не
  отвечает никогда — это уже обрыв туннеля, а не медленный запрос.
