Записано в день принятия, по образцу 22.08, 05.09 и волн M/R (06.09). Спека:
`docs/superpowers/specs/2026-09-06-wave-a1-mcp-cli-design.md` (решения Р-1…Р-9 в §3, требования

## Р-1. Один клиент на два входа

**Решение: `apps/mcp` содержит и MCP-сервер, и CLI — они разные оболочки над одним модулем
`core-client.ts` (fetch + токены + разбор ошибок, 21 метод). Отвергнуто: CLI отдельным пакетом
(дублирует клиент и релизный путь), CLI внутри `tools/` (там нет workspace-пакета и типов).**

**Почему.** В репозитории уже было четыре несовместимые копии похода в Core: `tools/*.mjs` (25
скриптов, копипаст `CORE_API_URL ?? http://127.0.0.1:3001` + `x-service-token`), TS-клиент панели
(`apps/cc/src/lib/core.ts`, `server-only`), клиент агентов (`apps/agents/src/core-client.ts`) и
Core-сервисы напрямую. Ни один из них не годится MCP/CLI без переписывания (сборка, типы,
рантайм-окружение) — пятая копия того же fetch была бы просто следующей несовместимой копией.

**Цена ошибки.** Общий клиент — общая точка правки: перевод ошибок (Р-9), таймаут, owner-заголовок
меняются один раз и действуют одинаково в MCP и CLI. Разъехавшиеся копии означали бы, что owner-токен
уходит по-разному из двух оболочек одного и того же среза — обнаружилось бы не тестом, а инцидентом.

## Р-2. Инструменты именуются `<область>_<действие>` и делятся по последствию

**Решение: восемнадцать инструментов (`apps/mcp/src/tools.ts`, `READING_TOOLS` + `MUTATING_TOOLS`):
двенадцать читающих (`briefing_get`, `inbox_list`, `tasks_list`, `task_get`, `registry_search`,
`events_recent`, `memory_recall`, `kb_read`, `kb_tree`, `agents_list`, `runs_recent`,
`ventures_list`) и шесть меняющих мир (`task_create`, `task_comment`, `task_status`,
`memory_remember`, `agent_upsert`, `approval_decide`). Описание каждого меняющего инструмента
первым предложением говорит, что именно он изменит и где владелец это увидит.**

**Почему.** Плоское пространство имён `<область>_<действие>` вместо, например, `tasks.list` —
потому что MCP-инструменты у разных серверов часто плоские идентификаторы, а не иерархию, и модель
должна отличать читающий инструмент от меняющего по одному взгляду на список, без вызова. Первое
предложение описания — не украшение: модель решает, вызывать ли меняющий инструмент, читая только
описание, а не код.

**Цена ошибки.** Инструмент без чёткого «что изменится и где видно» рискует быть вызван моделью
вслепую («наверное, это безопасно») — цена такой ошибки для меняющих инструментов настоящая (задача,
согласование, карточка агента), поэтому дисциплина описания — не стиль, а часть контракта
безопасности среза (см. §5 спеки).

## Р-3. Правда о поясе безопасности — в описании инструмента, а не в намерении

**Решение: сервер при старте читает `GET /system/config`, запоминает состояние
`OWNER_IDENTITY_ENFORCED` и наличие owner-токена в своём окружении (`readPosture`, `server.ts`).
Описание `approval_decide` собирается динамически (`describeApprovalDecide`, `tools.ts`) под
фактическое состояние: пояс выключен / включён с токеном / включён без токена / неизвестен. Owner-
заголовок закладывается в клиент сразу, независимо от прочитанного состояния.**

**Почему.** Написать в описании статичное «только владелец» и надеяться, что Core это обеспечит —
ложь, которую владелец обнаружил бы поздно, в момент отказа (или хуже — в момент, когда отказа не
случилось, потому что пояс всё это время был выключен, а модель считала его включённым). Динамическое
описание переживает включение пояса без правки кода MCP: `readPosture` перечитывается при каждом
старте сервера, а не один раз при написании инструмента.

**Цена ошибки.** Если бы состояние пояса угадывалось, а не читалось, — при включённом поясе без
owner-токена модель вызвала бы `approval_decide`, получила бы 401 без предупреждения, и владелец не
понял бы, почему решение «не прошло». `beltUnknown` (Core не ответил на `GET /system/config`) —
отдельная честная ветка: сервер не выбирает удобный ответ, когда не знает правды.

## Р-4. Личный контур исключается явно, а не гардом

**Решение: `PersonalDomainGuard` Core не закрывает безадресные чтения (признанный обход,
`personal-domain.guard.ts:19-33` — гейт видит только запросы с явным селектором домена). Поэтому
`registry_search` и `tasks_list` по умолчанию отсеивают `domain != personal` НА СТОРОНЕ MCP,
фильтрацией уже полученного ответа (`hidePersonal`, `tools.ts`), а не запросом — у Core нет фильтра
«не personal», только `domain = X`. Достать личное можно только явным `domain: "personal"`, и такой
вызов уходит с owner-токеном (`personal(domain)` в `core-client.ts`). `kb_read` полагается на
серверную проверку `personalVisible` и честно возвращает её отказ, а не подменяет своей логикой.**

**Почему.** Два пути рассматривались и оба отвергнуты: заводить в Core параметр `domain != personal`
ради одного нового клиента — лишняя площадь API ради частного случая; молча ничего не фильтровать и
полагаться на `PersonalDomainGuard` — прямое нарушение спеки (§5: личный контур скрыт по умолчанию),
потому что гард именно эти запросы не закрывает по конструкции.

**Цена ошибки.** Отсев по ответу, а не по запросу, означает: **страница может вернуться короче
запрошенного `limit`** (например, попросили 50, десять из них — personal, отфильтровано, осталось
40). Это документированное ограничение (`docs/MCP.md` → «Ограничения»), а не баг — цена этой честной
неполноты кратно меньше, чем цена молчаливого показа личных задач в общем поиске без явного запроса.

## Р-5. Ответы — компактный текст, а не сырой JSON

**Решение: общие форматтеры (`apps/mcp/src/format.ts`) отдают готовые к чтению строки — список по
одной строке на запись (id, тире, возраст/статус), а не сырой payload Core. Полный объект отдаётся
только когда инструмент адресный (`task_get`, `kb_read`). Пределы: список ≤ 50 записей по умолчанию
(`MAX_LIST_ITEMS`), текст ответа ≤ 8000 символов (`MAX_RESPONSE_CHARS`, `clamp`), `kb_read` ≤ 64 КБ
по байтам UTF-8 (`MAX_KB_BYTES`, `truncateUtf8`) с честной пометкой об обрезке. Одна и та же форма
вывода используется MCP-инструментами и CLI-командами без `--json`.**

**Почему.** Сырой JSON Core (вложенные `attrs`, полные объекты задач и событий) раздувает контекст
модели и провоцирует галлюцинации о полях, которых в ответе не было («агент придумывает» несуществующий
атрибут по аналогии с похожими данными в обучении). Компактный текст с явными лимитами — модель видит
ровно то, что реально есть, и явную пометку, когда список или документ обрезаны, вместо тихого среза.

**Цена ошибки.** `limit: 1000` от модели не должен ни падать (400), ни тащить тысячу строк в контекст
— поэтому `limitOf` в `tools.ts` тихо срезает запрошенное к потолку `MAX_LIMIT = 200`, но честно
пишет об этом в описании параметра. Обрезка `kb_read` считает БАЙТЫ UTF-8, а не символы: кириллица —
два байта на букву, посимвольная обрезка соврала бы о фактическом размере документа примерно вдвое.

## Р-6. Микрофиксы Core минимальны и полезны сами по себе

**Решение: (а) `GET /events` принимает `source`, `limit` (1…200, дефолт остаётся прежним — 100,
см. Ruling 1 ниже), `until`, `order` (`asc|desc`); (б) `GET /events` принимает `typePrefix` —
префиксный фильтр по типу (`like` по `type`), чем перечисляется память агента (`agent.memory:`);
(в) `GET /agents/skills` принимает `agent`; (г) `GET /routines/runs` принимает `from`/`to`. Ни одной
миграции.**

**Почему.** Дыра была одна и точная: контроллер `EventsController.list` до волны A1 передавал в
сервис только `type` и `since`, хотя сервис уже умел `source`/`until`/`order`/`limit` — соседние
`count`/`latest` эти поля уже принимали, лента — нет. Остальные три фикса — та же форма: сервис уже
делал нужное, контроллеру не хватало одного query-параметра.

**Цена ошибки.** Ноль для существующих потребителей: все четыре фикса — новые ОПЦИОНАЛЬНЫЕ
параметры, ни один существующий вызов (`CoreClient.listEvents` в `apps/agents`, панель) не перестал
работать (проверено ревью Task 1 по коду, не по отчёту — ни один вызывающий в репозитории не шлёт
полей, которые теперь стали бы 400).

## Р-7. Сухой прогон CLI — одна конвенция

**Решение: у команд CLI, меняющих мир (`task-create`, `decide`), обязателен явный `--yes`: без него
— печать намерения и выход с кодом 0, Core не вызывается. Существующие `tools/*.mjs` не трогаем, но
конвенция зафиксирована в `docs/AGENTS_ACTIVATION.md` для новых скриптов.**

**Почему.** Старые `tools/*.mjs` проверяют флаги через `argv.includes(...)` — опечатка в имени флага
молча становится «флаг не передан», и скрипт делает не то, что хотел вызывающий, без единого
предупреждения. Разбор флагов CLI `mydon` (`apps/mcp/src/args.ts`) — свой, без зависимостей:
неизвестный флаг — всегда ошибка (с подсказкой при близком совпадении), а сухой прогон — явное
поведение по умолчанию для любой команды, которая пишет в Core.

**Цена ошибки.** Без этой конвенции `mydon task-create --title "…"` без `--yes` создавал бы задачу
сразу — ошибка в одной интерактивной команде превращается в лишнюю задачу в Core, которую придётся
искать и удалять вручную. С конвенцией худший случай — увидеть напечатанное намерение и повторить
команду с `--yes`.

## Р-8. Сборка и доставка

**Решение: `apps/mcp` — обычный пакет workspace (`@mydon/mcp`), TypeScript, сборка в `dist`,
`bin: { mydon: "dist/cli.js" }`. В `deploy/Dockerfile` — одна строка `COPY apps/mcp/package.json
./apps/mcp/` в слое зависимостей (нужна для целостности `pnpm install --frozen-lockfile`). На
сервере ничего не запускается: MCP живёт у владельца на MacBook и ходит в Core через SSH-туннель.
`.mcp.json` в корне репозитория описывает сервер для Claude Code; секреты в нём не хранятся —
только имена переменных окружения (`${VAR:-default}`, синтаксис подтверждён по документации Claude
Code).**

**Почему.** MCP-сервер по своей природе — процесс на машине пользователя, говорящий по stdio с
локальным Claude Code; запускать его на сервере бессмысленно (там нет stdio-клиента, который бы к
нему подключился) и не нужно (владелец — единственный пользователь). `COPY apps/mcp/package.json`
в Dockerfile — не запуск, а требование самого `pnpm install` в workspace: без манифеста пакета
общий лок-файл не разрешится для остальных приложений образа.

**Цена ошибки.** Ноль для прода: `apps/mcp` не участвует в рантайме сервера, добавление пакета не
меняет поведение уже задеплоенных `core`/`agents`/`bot`/`cc`/`watchdog`.

## Р-9. Ошибки Core переводятся, а не пробрасываются

**Решение: `translate()` в `core-client.ts` — 401 → «Core не принял токен: проверь SERVICE_TOKEN…»,
403 → «личный контур закрыт: нужен owner-токен» (+ текст Core, если он есть), 404 → «не найдено:
<путь>», 409 → текст Core как есть (конфликт объясняет сам Core лучше любого пересказа), 429 →
«Core ограничил частоту, повтори через несколько секунд», сеть/таймаут → «Core недоступен по адресу
…: <причина>». Ни одно сообщение не печатает значение токена ни при каком коде.**

**Почему.** Сырой код ответа Core («401») ничего не говорит модели или владельцу о том, что делать
дальше; переведённое сообщение называет конкретную переменную окружения, которую нужно проверить.
Тело ответа читается в той же защите от таймаута, что и заголовки (`fetchBody`): обрыв туннеля или
срабатывание таймаута посреди потока тела иначе выбросил бы сырой `DOMException`/`TypeError` уже
после проверки статуса — мимо единственного контракта модуля (`CoreError`).

**Цена ошибки.** Пустое тело на успехе (`ok: true`, пустая строка) — тоже `CoreError`, а не тихий
`undefined` под объявленным типом: все обёрнутые маршруты Core всегда отдают JSON, и молчаливый
`undefined` уронил бы форматтер в рантайме при незамеченном компиляторе типе (найдено ревью Task 2 —
исходная реализация делала `return undefined as T`, что ломало объявленные типы).

## Ruling из ревью (родились не в спеке, дописаны по факту)

Три решения приняты во время реализации (задачи 1 и 4), а не заранее в спеке. Каждое
задокументировано в леджере `.superpowers/sdd/2026-09-06-wave-a1-mcp-cli/progress.md` в момент
принятия; здесь — сведены вместе с причиной и ценой ошибки.

### Ruling 1 — дефолт `GET /events` остаётся 100, лимит 50 шлёт сам MCP

**Решение: дефолт страницы `GET /events` НЕ меняется ради MCP — остаётся 100, как было до волны A1.
Лимит 50 (Р-5) — предел ОТВЕТА MCP, который сервис `events_recent`/CLI `events` шлёт явным
query-параметром `limit=50` (или другим значением по запросу). Спека §4.4 поправлена этим ruling'ом
(коммит `5dc3bb9`).**

**Почему.** Менять поведение существующего потребителя (`CoreClient.listEvents` в `apps/agents`,
завязанного на дефолт 100) ради удобства нового клиента нельзя — это молчаливая правка контракта
маршрута, которую существующий читатель не просил и не заметит до момента, когда данные начнут
отличаться от ожидаемых. MCP умеет и обязан просить явный лимит — у него нет причины полагаться на
чужой дефолт.

**Цена ошибки.** Найдено в ревью реализации Task 1, до мержа. Если бы дефолт поменяли на 50 — любой
существующий вызов `GET /events` без `limit` (в том числе `apps/agents`) молча получал бы вдвое
меньше записей, чем раньше, без единой строки в логе об изменении поведения.

### Ruling 2 — узкое DTO для `count`/`latest`: неизвестное поле снова 400

**Решение: `count`/`latest` НЕ разделяют DTO с лентой (`ListEventsDto`) — у них отдельный
`FilterEventsDto` с прежним набором полей (`type`, `source`, `since`). Новые поля волны A1
(`typePrefix`, `until`, `order`, `limit`) на `count`/`latest` снова дают 400 «неизвестное свойство»,
как и любое незнакомое поле до этой волны.**

**Почему.** Если бы `count`/`latest` унаследовали общий с лентой DTO, они начали бы ВАЛИДИРОВАТЬ, но
МОЛЧА ИГНОРИРОВАТЬ поля вроде `typePrefix` (эти маршруты их не читают и не читали) — вызывающий
получил бы `200 OK` со счётчиком/записью, посчитанными без фильтра, который он явно попросил. Это
хуже прежнего поведения (400 на неизвестное поле): 400 — явная и мгновенная подсказка «этот параметр
здесь не работает»; тихое 200 с неверным числом — ошибка, которую замечают не сразу и не всегда.

**Цена ошибки.** Найдено в ревью реализации Task 1 (тот же коммит `5dc3bb9`, спека §4.4 поправлена).
Цена, если бы не поправили: `memory_recall` без явного `skill` в теории мог бы использовать `latest`
с `typePrefix` и получить «самое свежее событие БЕЗ учёта префикса» вместо ожидаемой памяти
конкретного навыка — молчаливо неверный ответ владельцу о том, что агент «помнит».

### Ruling 3 — `kb_tree` остаётся в наборе, инструментов восемнадцать

**Решение: инструмент `kb_tree` (дерево страниц знаний, `GET /docs/tree` с локальной фильтрацией по
`root`) сохранён в финальном наборе — восемнадцать инструментов, а не семнадцать. Спека §3 (Р-2)
поправлена этим ruling'ом (коммит `8f2ef5d`) — итоговая формулировка «семнадцать плюс `kb_tree`»
приведена к прямому счёту «восемнадцать».**

**Почему.** Без дерева страниц модель не может узнать, какой путь просить у `kb_read`: белый список
корней (`docs/`, `memory/`, `routers/`…) она не видит иначе, а угадывание пути по названию — источник
404 и потраченных вызовов. §4.2 спеки всегда требовал `kb_tree` («дерево `GET /docs/tree`, чтобы
модель знала, что просить») — расхождение было только в итоговой цифре Р-2, не в решении иметь
инструмент.

**Цена ошибки.** Найдено в реализации Task 4 — редакционное расхождение в спеке (посчитано «семнадцать»
при живом перечислении восемнадцати), а не архитектурный вопрос. Цена ошибки нулевая: правка — только
формулировка счёта в спеке, код и тесты (134 pass) с самого начала включали `kb_tree`.

## Что решением НЕ отменяется

- «Личный контур скрыт по умолчанию» (Р-4) — правило для ЛЮБОГО будущего инструмента/команды CLI,
  которые читают `tasks`/`entities` безадресно: фильтровать ответ, а не полагаться на
  `PersonalDomainGuard`, пока follow-up R-P5-7 (аудит доступа к personal) не закроет пробел в Core.
- «Меняющий инструмент — одна операция за вызов» (§5 спеки) — ни один будущий инструмент/команда не
  получает пакетного режима без отдельного явного решения.
- «Ошибка Core переводится, токен никогда не печатается» (Р-9) — правило для любого нового метода
  `core-client.ts`.
