## Р-1. Зеркала движка — под тестом дрейфа, не генерируются

**Решение: `engine/autonomy.yaml` и `engine/eval-rubric.md` остаются рукописными
читаемыми копиями кода (`policy.ts`, `tools.ts`, `skill-loader.ts`, `coach.ts`,
`coach-review.ts`). Расхождение ловит тест `apps/agents/src/engine-mirror.test.ts`,
а не генератор.**

**Почему.** Два пути закрывали «51 битую ссылку из паспортов, указывающую на
`engine/`»: сгенерировать файлы из кода или написать их руками и сверять тестом.
Генератор отдал бы то же самое, что уже есть в коде, — голые числа и имена без
объяснения, зачем тир именно такой. Ценность `engine/*.md` для владельца и
агентов — в прозе рядом с фактами («почему `exec` начинается с T2», «почему
`PASS_THRESHOLD` такой»), а не в самих числах: их и так можно прочитать в TS.
Рукописный файл с тестом-сторожем даёт то же самое отсутствие дрейфа, что и
генератор, но не теряет объяснение.

**Цена ошибки.** Если тир, вес рубрики или дефолт `AGENT_AUTONOMY_MAX` поменяются
в коде без правки зеркала — CI краснеет на `engine-mirror.test.ts` до мержа, а не
после того, как агент прочитал устаревшее правило. Ложных срабатываний тест не
даёт: он сверяет факты (имена, пороги, порядок), а не форматирование прозы.

## Р-2. Документы отдаёт Core с диска образа, за сервисным токеном и на GET

**Решение: `GET /docs/tree|file` читают файловую систему Core (`COPY . .` в
образе), а не GitHub и не файловую систему CC. Белый список корней и
расширений — единственный вход. `DocsTokenGuard` требует `x-service-token` и на
чтение — не так, как остальной read-only API Core, где GET открыт. Личные корни
(`memory/**`, `routers/personal.md`, профиль владельца из навыка фабрики
направлений) добавлены в ревью: содержимое отдаётся только по owner-токену
(`personalVisible`), а не по общему сервисному.**

**Почему.** У панели `apps/cc` нет доступа к файлам образа `mydon-core` — это
разные контейнеры. Три пути были: панель тянет GitHub API (сеть наружу и токен
GitHub в оболочке — лишняя поверхность и лишний секрет), CC читает свою копию
репозитория (второй источник истины, разъезжается с тем, что реально
задеплоено), Core отдаёт то, что у него уже есть на диске. Третий путь бесплатен:
образ и так собирается `COPY . .` ради паспортов агентов, а `docs/`, `memory/`,
`routers/`, `engine/` лежат там же.

`SERVICE_TOKEN` общий — его держат бот и агенты, а не только владелец, поэтому
«за сервисным токеном» само по себе не защита личного контура: `memory/`
содержит handoff-заметки и личные наблюдения. Отдельный `DocsTokenGuard` вместо
переиспользования глобального `ServiceTokenGuard` — потому что тот пропускает
GET намеренно (реестр, продажи, задачи читают все в закрытой сети), а документы
таким открытым быть не должны. Личный контур добавлен уже в ревью ветки, не в
исходной спеке: без него дерево показывало бы содержимое `memory/**` любому, у
кого есть общий токен агентов, — то же самое нарушение, ради недопущения
которого писался `PersonalDomainGuard` для остального API.

**Цена ошибки.** Утечка внутренних решений и переписки с самим собой наружу
(если токен утечёт вместе с остальными секретами Core) — тот же класс риска, что
у остального API за `SERVICE_TOKEN`, ничем не хуже. Без owner-пояса на личное —
любой держатель общего токена (бот, агенты) читает заметки владельца о себе:
закрыто явной проверкой `isPersonalDoc` + `personalVisible` до чтения файла.

## Р-3. Граф строится в Core, включая рёбра `mentions` по путям в бэктиках

**Решение: `GET /docs/graph` собирает узлы и рёбра в Core из тех же файлов, что
и дерево, плюс живые агенты и каталог навыков из базы. Кроме рёбер `links`
(настоящая markdown-ссылка `[текст](путь)`) граф считает `mentions` — путь,
упомянутый в обратных кавычках (`` `routers/vendhub.md` ``), если он указывает
на существующий файл из белого списка.**

**Почему.** Первая версия строила граф из одних `links`. На реальном репозитории
(208 файлов из белого списка) настоящих markdown-ссылок оказалось всего 25 —
граф распадался на десятки изолированных островов, и «Мозг» не показывал бы
никакой связности между документами, которые ссылаются друг на друга ровно так,
как принято писать в этом репозитории: путём в кавычках внутри прозы
(`«см. routers/dev.md»`), а не markdown-синтаксисом. Без `mentions` панель не
соответствовала бы факту — не «граф репозитория», а «граф 25 ссылок».
`mentions` не создаёт рёбер на несуществующее (проверка `exists`) и не дублирует
`links` на ту же пару (настоящая ссылка сильнее упоминания).

**Цена ошибки.** Ложное ребро `mentions` возможно только на путь, который
одновременно похож на файловый (`\w+\.(md|yaml)`) и реально существует в белом
списке, — то есть либо документ действительно про него говорит, либо совпадение
имени файла с текстом в кавычках. Второе безвредно: лишнее ребро в «Мозге»
хуже отсутствующего не считается, граф остаётся читаемым: легенда объясняет три
плотности линий (структура · ссылки · упоминания) отдельным рядом образцов.
Наведения на рёбра у холста нет и не планируется — это canvas, а не DOM.

## Р-4. Рендер markdown — `marked` в панели, с экранированным сырым HTML

**Решение: `apps/cc/src/lib/markdown.ts` — свой `Renderer` поверх `marked`:
блоки сырого HTML не исполняются, а экранируются в текст; ссылки внутри
репозитория переводятся на `/docs?path=…`, внешние получают
`target=_blank rel=noopener`. В ревью найден и закрыт баг: текстовый токен,
идущий ПОСЛЕ сырого HTML-блока, marked помечает `escaped: true`, и дефолтный
`text()` печатает его КАК ЕСТЬ — без экранирования вовсе (18.0.11,
воспроизведено). Переопределён `renderer.text()`; экранирует отдельная
`escapeText`, которая не удваивает уже готовые мнемоники (иначе валидный
`&amp;` стал бы `&amp;amp;`).**

**Почему.** Источник документов доверенный — свой репозиторий, — но его правят
агент (правка через approval — не в этом срезе, но планируется), владелец с
телефона и `git`; один `<script>` или `<img onerror=…>` в документе получил бы
права страницы `/docs` вместе с сервисным токеном, который серверные экшены CC
держат в памяти процесса. Правило «панель не исполняет чужой HTML» дешевле, чем
разбор исключений «а этот файл можно, он мой». Найденный в ревью XSS был именно
такой дырой: `renderer.html` экранировал сам сырой блок, но не следующий за ним
текстовый узел — воспроизведено на настоящей версии `marked`, подтверждено
тестом до фикса и после.

**Цена ошибки.** Пропущенный сырой HTML в документе исполнился бы в контексте
`/docs` с доступом к тем же cookie/токенам, что у остальной панели, — полноценный
XSS с той же матрицей риска, что у стандартной уязвимости в CMS. Закрыто на
уровне рендерера (одна функция, один тест на регресс), а не точечным фильтром.

## Р-5. Граф «Мозг» — `d3-force` на canvas в клиентском компоненте

**Решение: `/brain` рисует граф `<BrainGraph>` — клиентский компонент,
`d3-force` (link/charge/center/collide) поверх `<canvas>`, drag узлов, колесо —
zoom, легенда `.chip` по видам узлов, поиск сужает граф до совпадений и
соседей, клик открывает карточку `.panel.console` справа.**

**Почему.** Стандартная сила `d3-force` — готовое решение для «граф со связями,
где важно не пересечение рёбер, а кластеры»: писать свой физический движок ради
~300 узлов не за что. Canvas, а не SVG — потому что при таком количестве узлов и
рёбер SVG DOM разрастается до тысяч элементов и тормозит drag/zoom, а canvas
перерисовывает кадр целиком без накопления узлов в DOM.

**Цена ошибки.** `d3-force` — зависимость с своим жизненным циклом обновлений;
версия зафиксирована в `package.json`, апгрейд — обычный PR с прогоном
`brain-graph.test.tsx` (canvas в тесте мокается, логика поиска/карточки — нет).

## Р-6. Правка документов агентом через approval — не в этом срезе

**Решение: панели `/docs` и `/brain` — только чтение. Механизма
«coach-diff для произвольного документа» в коде нет (есть только
`coach-apply.ts` для `SKILL.md` навыков).**

**Почему.** План ARМS (§6.2 п. 5) называл правку документов агентом через
approval среди задач волны M. На деле это отдельный контур: нужен diff-формат,
превью изменений владельцу, approval-карточка с типом «правка документа» и
применение diff к файлу образа (который через `COPY . .` не переживает
редеплой без коммита в репозиторий — то есть правка агента обязана стать git-
коммитом, а не просто записью на диск контейнера). Существующий `coach-apply.ts`
решает узкую задачу — применение вердикта coach-review к `SKILL.md` — и не
обобщается на произвольный markdown без отдельного проектирования. Делать это
одним куском со срезом про чтение значило бы утроить объём среза ради функции,
которую никто ещё не запросил.

**Цена ошибки.** Ноль для этого среза: чтение не деградирует, если правка
появится позже, — она добавится сверху, панель для чтения не переписывается.
Правка документов остаётся ручной (через `git`), как и раньше волны M.

## Р-7. RAG не включается этим срезом

**Решение: `docs/FIRST_LOGIN_CHECKLIST.md` получает пункт «Включить RAG» со
ссылкой на `docs/AGENTS_ACTIVATION.md` → «Сценарий 2» и точными именами env
(`EMBED_BASE_URL`, `EMBED_MODEL`, `EMBED_PRICE_PROVIDER_ID`, `EMBED_BILLING_MODE`).
Сам RAG не поднимается.**

**Почему.** Семантическая память требует OpenAI-совместимый `/embeddings`
endpoint — инфраструктуру и (в `metered`-режиме) реальные деньги владельца по
тому же ledger, что и остальные LLM-вызовы. Решение поднять внешний endpoint,
выбрать провайдера ценового каталога и включить биллинг — не техническое, а
денежное и инфраструктурное, и по правилу репо («агент ничего не делает сам без
тира», деньги — T3) включается только владельцем осознанно, не «заодно» с
срезом про панель документов.

**Цена ошибки.** Без RAG `assess-ideas` продолжает работать без памяти о ранее
разобранных идеях (текущее поведение, не регресс). Включение — одна правка
`.env` и рестарт, обратимо: `EMBED_BILLING_MODE` не задан → память просто не
поднимается, ничего не ломается.

## Р-8. `PROTOCOL.md` / `MYDON_AGENT_BUILDER.md` — оригиналы утеряны, перенос по фрагментам

**Решение: `PROTOCOL.md` и `MYDON_AGENT_BUILDER.md` НЕ переносятся — их не
нашли ни в одном доноре и ни в одном локальном чекауте (`chat-historian`,
06.09.2026: оригиналы жили в чатах claude.ai, июнь–июль 2026, и не сохранились
на диске). Вместо переноса — три источника, которые СЕЙЧАС покрывают ту же
функцию: шаблон `apps/agents/agents/_template/` (структура паспорта нового
агента), `apps/agents/shared/kb/venture-factory/direction-package.md` (пакет
направления для Builder-фазы фабрики) и контракт запуска `run-log.v1.0`,
восстановленный дословно из фрагмента истории чатов и перенесённый в
`apps/agents/shared/kb/protocol/run-log.md`.**

**Почему.** `docs/agentic-os-starter/APPLY.md` и `memory/open-questions.md` уже
04.09 фиксировали «`PROTOCOL.md` и `MYDON_AGENT_BUILDER.md` в донорах не
найдены» как открытый вопрос. Целенаправленный поиск по всей истории чатов
(Claude Code, Codex, Cursor, импортированный claude.ai) через `chat-historian`
подтвердил: содержимое файлов нигде не сохранено — есть только упоминания
существования («Agent Protocol PROTOCOL.md v1.1, 12 принципов, 7-фазный
жизненный цикл») в памяти claude.ai проекта `mydon-agentos`, но не сам текст.
**Придумывать содержимое утерянного файла по названию — хуже, чем честно не
переносить его**: PROTOCOL.md на 12 принципов, реконструированный по одной
строке памяти, выглядел бы авторитетным источником, а был бы вымыслом ассистента
задним числом. Run-log — исключение: единственный документ, который
восстановился ЦЕЛИКОМ (не пересказом, а дословным фрагментом с версией и датой),
и уже описывает контракт, которому агенты MYDON фактически следуют (семь фаз,
статусы, схема JSON) — перенесён как есть, с пометкой источника и даты
восстановления, без единой придуманной строки.

**Цена ошибки.** Отсутствие переносимого PROTOCOL.md не блокирует работу
агентов: `run-log.md` описывает контракт исполнения, `_template/` — структуру
паспорта, `direction-package.md` — пакет для Builder-фазы; это то же самое, что
план ARMS уже называл заменой («агенты пишутся по `_template/` и
`direction-package.md`»). Если оригиналы найдутся позже (экспорт claude.ai,
пункт в `FIRST_LOGIN_CHECKLIST.md`) — перенос дописывается отдельным срезом без
переделки того, что уже есть.

## Что решением НЕ отменяется

- «Панель не исполняет чужой HTML» (Р-4) — правило для ЛЮБОГО будущего рендера
  markdown в оболочке, не только `/docs`.
- «Агент ничего не делает сам без тира»: RAG и правка документов остаются вне
  автономии агента, включаются/утверждаются владельцем (Р-6, Р-7).
- Источник истины о зеркалах движка — код (`policy.ts` и соседи); `engine/*`
  читаемая копия, а не наоборот (Р-1).
- «Секретов в панели нет»: `/docs` и `/brain` не показывают ничего, чего Core
  не отдал бы по тем же правилам API.

## Отложено сознательно

- Правка документов агентом через approval (§6.2 п. 5, Р-6) — волна R/A.
- RAG (Р-7) — решение и инфраструктура владельца.
- `PROTOCOL.md` / `MYDON_AGENT_BUILDER.md` дословно (Р-8) — только если найдётся
  экспорт claude.ai; реконструкция по памяти не рассматривается.
- Кластеризация узлов `/brain` по направлению (визуальная группировка `domain:*`
  крупнее остальных) — косметика, не инвариант; текущая раскладка `d3-force`
  достаточна для < 300 узлов.
