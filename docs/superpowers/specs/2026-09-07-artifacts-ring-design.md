# Срез A3 «Кольцо артефактов» — спека

**Дата:** 2026-09-07
**Волна:** A, §6.4 п. 4 плана ARMS
**Основание:** проверка премисы — `.superpowers/sdd/notes/2026-09-06-a3-artifacts-premise.md`

---

## 0. Премиса плана не подтвердилась — и срез от этого стал нужнее

План §6.4 п. 4 говорит: «Кольцо артефактов (`/artifacts`): всё, что произвели
агенты и Claude Code — `document` (КП docx, отчёты навыков, clone-spec),
coach-diff, экспорт… **Данные уже в Core — нужна витрина.**»

Проверено по коду, и это неверно в обе стороны:

- **Таблица `document` мёртвая.** Объявлена в схеме, но во всём монорепо в неё
  никто не пишет и никто не читает; модуля `documents` в Core нет. Витрина над
  ней показывала бы пустой экран всегда.
- **КП и договоры не сохраняются.** `kp.controller.ts` и
  `contracts.controller.ts` рендерят docx в буфер и отдают потоком — «рендер
  без побочных эффектов», как сказано в комментарии.
- **Документы при этом РЕАЛЬНО производятся и тут же теряются.** Пакет
  `@mydon/documents` делает Excel, Word, PowerPoint, PDF через навыки Anthropic
  с исполнением кода в контейнере. Единственный потребитель — Telegram-бот,
  который файл **отправляет и не сохраняет** (`apps/bot/src/index.ts`,
  ветка `reply.document`). При сбое отправки файл потерян совсем, пользователю
  пишут «повтори запрос». Документ, стоивший вызова модели с исполнением кода,
  живёт секунды.

Значит срез начинается не с витрины, а с **письма**: дорогая работа должна
перестать пропадать. Витрина — вторая половина.

**Критерий плана переформулирован честно.** Было: «артефакт трёхнедельной
давности находится за 10 секунд». Для документов, созданных до среза, это
недостижимо — их не существует. Стало: *любой артефакт, произведённый после
выката среза, находится по типу, владельцу и дате за 10 секунд; про время до
среза экран говорит прямо, а не показывает пустоту как «ничего не было».*

---

## 1. Субстрат: `attachment`, а не `document`

Решение контроллера с причинами.

**За `attachment`:** у неё живое хранилище (`StorageService`: S3 через
`STORAGE_*` или локальный каталог), пять маршрутов (`POST`, `GET`, `GET /batch`,
`GET /:id`, `GET /:id/raw`), настоящие строки от полевого контура (фото,
чеки), и `ownerType` уже задуман расширяемым («`entity` | `stock_movement` |
…»). Артефакт агента — это ещё один `ownerType`, а не новая сущность.

**Против `document`:** ноль кода. Оживить её — значит либо построить второе
хранилище, либо продублировать `attachment`. Оба варианта хуже.

**Что с `document` делать:** НЕ удалять в этом срезе. Таблица пуста, но снос
таблицы — необратимая операция, а фокус среза — письмо артефактов, не уборка.
Помечается в схеме комментарием как устаревшая, сносится отдельным решением
владельца, когда `/artifacts` поработает.

**Чего у `attachment` нет, и что даёт миграция** (единственная в волне A):
- `title text` — человеческое имя артефакта («Дебиторка GLOBERENT за август»),
  сейчас есть только `storageKey`;
- `domain` — направление бизнеса (тот же `domainEnum`, что у `money_flow`),
  чтобы искать «всё по VendHub»;
- `tags jsonb default '[]'` — то, ради чего `document` и заводили;
- индекс `(kind, created_at desc)` под витрину «последние артефакты такого
  рода» — сегодня есть только `(owner_type, owner_id)`.

**Ловушка: `ownerId uuid NOT NULL`.** Документ, который бот сделал по чат-
запросу, не привязан ни к задаче, ни к сущности. Вариантов три:
1. сделать `ownerId` nullable — ломает инвариант «у вложения есть хозяин»,
   на котором стоит полевой контур;
2. привязывать к `person` (кто попросил) — у бота есть `chatId`, и оператор
   резолвится в `person` (память: «доступ решает `person.roles`»);
3. заводить «синтетического» владельца — плохо, это выдумка.

**Решение: вариант 2.** `ownerType = "person"`, `ownerId` = тот, кто попросил.
Это правда: документ произведён для этого человека. Если запрос шёл из задачи
(будущее: агент сделал отчёт по задаче) — `ownerType = "task"`. Оба уже
существуют как сущности с UUID.

## 2. Что делает срез

### 2.1. Письмо: бот сохраняет документ ДО отправки

В `apps/bot/src/index.ts`, ветка `reply.document`: сначала `POST /attachments`
(`ownerType: "person"`, `kind: "doc"`, `title` из `doc.summary` или
`filename`, `mime` по расширению, `domain` если бот его знает), потом
`tg.sendDocument`. Если сохранение не удалось — отправка всё равно идёт (файл
у нас в руках, терять его из-за хранилища нельзя), но в лог уходит причина и в
ответ пользователю — короткая строка «в архив не лёг». Если отправка не удалась,
а сохранение удалось — пользователю говорят, что файл в архиве, и дают на него
ссылку в панель. **Прежнее «повтори запрос» исчезает**: повторять больше
незачем.

### 2.2. Чтение: `GET /artifacts` в Core

Новый маршрут, закрытый `ReadTokenGuard` (как все читающие двери с содержанием
работы агентов): список вложений с фильтрами `kind`, `ownerType`, `ownerId`,
`domain`, `from`/`to` по `createdAt`, `q` по `title` (ILIKE), пагинация
`limit`/`cursor`. Отдаёт строки БЕЗ содержимого; содержимое — существующим
`GET /attachments/:id/raw`.

Существующий `GET /attachments` остаётся как есть (он требует
`ownerType`+`ownerId` и обслуживает полевой контур).

### 2.3. Витрина `/artifacts` в панели

Экран командного центра (тёмный по Д2, если Д2 уже смержен; иначе через
`ConsoleTheme`, как соседи). Три фильтра сверху: тип (документ / фото / чек),
направление, период. Поиск по названию. Список — строками в грамматике Д1:
слово (тип), название, кто/для кого, направление, **давность** (`ago` из
`lib/format.ts`, часы Core). Открытие: docx/xlsx/pdf — ссылка на `raw`;
HTML — в новой вкладке.

**Пустое состояние говорит правду и называет дату.** «Артефактов с
<дата выката> ещё нет» — не «ничего не найдено». Дата выката — из самой
миграции (её `created_at` в журнале Drizzle) либо константой в коде с
комментарием, почему.

### 2.4. Навигация и навык

Пункт «Артефакты» в навигации командного центра. Маршрут добавляется в
`CONSOLE_ROUTES` (`lib/theme.ts`, если Д2 смержен) — и тогда `/artifacts` в
`rules.md` §4 наконец существует. `primitives.md` получает описание строки
артефакта.

## 3. Чего срез НЕ делает

- Не сохраняет КП и договоры при каждом рендере: они рендерятся владельцем по
  требованию, и автосохранение каждого черновика забило бы архив. Кнопка
  «в архив» у КП — отдельное решение после того, как `/artifacts` поработает.
- Не делает coach-diff и экспорт: их существование не подтверждено (заметка
  по премисе), обещать несуществующее нельзя.
- Не сносит `document`.
- Не заводит полнотекстовый поиск по содержимому — только по `title`.
- Не трогает полевой контур `attachment` (фото/чеки): их `ownerType` и
  маршруты как были.

## 4. Требования приёмки

- **Р-A3-1.** Документ, сгенерированный ботом, существует в `attachment`
  ДО того, как ушёл в Telegram. Сбой отправки не теряет файл.
- **Р-A3-2.** Сбой сохранения не блокирует отправку и назван пользователю
  словами, а не молча.
- **Р-A3-3.** `GET /artifacts` закрыт токеном, фильтрует по всем шести
  параметрам, пагинируется, и не отдаёт содержимого файлов.
- **Р-A3-4.** На `/artifacts` артефакт, созданный после выката, находится по
  типу + направлению + периоду или по названию не более чем за два действия.
- **Р-A3-5.** Пустое состояние называет дату, с которой архив ведётся, и не
  выглядит как «ничего не было».
- **Р-A3-6.** Строка артефакта печатает давность по часам Core (грамматика Д1),
  и словарь типов живёт в `lib/state.ts` (единственный дом — сторож Д1 это
  ловит).
- **Р-A3-7.** Миграция обратима и не трогает существующие строки `attachment`
  (новые колонки nullable или с default).
- **Р-A3-8.** `document` помечена устаревшей комментарием в схеме; в
  `docs/decisions/` записано, почему субстрат — `attachment`.

## 5. Проверки, которые должны упасть при откате

- Бот: мок хранилища возвращает ошибку → `sendDocument` всё равно вызван и
  пользователю ушла строка про архив.
- Бот: `sendDocument` бросает → строка в `attachment` есть, пользователю ушла
  ссылка.
- `GET /artifacts` без токена → 401; с токеном и `q=дебиторка` → только
  строки с таким `title`.
- Смоук на живом Postgres: `POST /attachments` с `title`/`domain`/`tags` →
  `GET /artifacts?domain=...` находит.
- Пустая витрина печатает дату, а не «ничего не найдено».

## 6. Ловушки, названные заранее

1. **Миграция — первая в волне A.** Прод — внешний Supabase через pooler;
   `ALTER TABLE attachment ADD COLUMN` на живой таблице с фото — быстро, но
   индекс `(kind, created_at)` строить `CONCURRENTLY`, иначе блокировка
   полевого контура. Проверить, умеет ли Drizzle-миграция `CONCURRENTLY`
   (в транзакции нельзя).
2. **Бот резолвит `person` по `chatId`** — если чат не сопоставлен человеку
   (гость), владельца нет. Решение: не сохранять и сказать об этом — гостю
   архив не положен, это честно и совпадает с правилом доступа бота.
3. **`GET /attachments/:id/raw` отдаёт файл по id без проверки владельца?**
   Проверить до выката витрины: если да, то `/artifacts` делает перебор id
   тривиальным. Закрыть тем же `ReadTokenGuard`.
4. **`title` из `doc.summary` может быть длинным** — обрезать до 120 символов
   на входе, полный текст остаётся в `caption` Telegram-сообщения.
5. **Порядок с Д2.** Если A3 выкатывается раньше Д2 — `/artifacts` берёт
   `ConsoleTheme`, как соседи, и Д2 его снесёт вместе с остальными. Если
   позже — сразу `CONSOLE_ROUTES`. План должен сказать, какой вариант, по
   факту на момент исполнения.

## 7. Решения контроллера

1. Субстрат — `attachment` (§1).
2. Владелец чат-документа — `person`, не nullable `ownerId` (§1).
3. Сохранение ДО отправки, сбой хранилища не блокирует отправку (§2.1).
4. КП/договоры — не в этом срезе (§3).
5. `document` не сносится, помечается (§1).
6. Критерий приёмки переформулирован под честность о прошлом (§0).
